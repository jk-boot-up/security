ONE. Full and incremental backups, with a manifest.
  day 1, a full backup: 3 files stored
  day 2, an incremental backup: 2 files stored (orders changed, refunds new)
  day 3, an incremental backup: 1 file stored
  the manifest of day 3 lists 4 files, each with its SHA-256
  restoring day 3 takes the newest copy of each file from the chain; problems found: 0
  incremental backups are small and quick, and a restore needs the whole chain
TWO. Can the backup be trusted? Only a restore test says.
  one byte of a stored file is changed: files found changed 1, and the manifest names it
  a stored file is deleted: files found missing 1
  a backup job skipped the orders file because it was in use; the manifest checks out: true
  the restore test asks for a usable orders file: false  <- A BACKUP NOBODY RESTORED IS A HOPE
  a good backup passes the restore test: true, with 3 orders
THREE. The 3-2-1 rule, and how long to keep backups.
  a copy in another folder of the same server: three copies false, two media false, one off site false, one unchangeable false: 0 of 4
  the server, a NAS and an off-site locked bucket: three copies true, two media true, one off site true, one unchangeable true: 4 of 4
  400 daily snapshots, keeping 7 daily, 4 weekly and 12 monthly: 21 kept, 379 pruned
  the oldest kept is 2025-03-01: a year of history in 21 snapshots instead of 400
  keeping less than the law or the business needs is a risk too, and so is keeping personal data for ever
FOUR. Ransomware, and the copy it cannot change.
  ransomware runs on the shop server and encrypts 3 files in place
  the orders file still reads as before: false
  the backup folder was mounted and writable, so it is encrypted too: 3 files  <- THE BACKUP WENT WITH THE DATA
  a store that only adds versions took the attacker's writes as new versions: 2 versions of the orders file
  restoring the version from before the attack gives every original file back: true
  files marked read-only: encrypted 0, blocked 3
  but the same user can make them writable again: encrypted 3  <- REAL PROTECTION COMES FROM A COPY THE SHOP'S OWN ACCOUNT CANNOT CHANGE
FIVE. How much can be lost, how long it takes, and backups as secrets.
  nightly backup at 02:00, failure at 15:30, noticed at 15:50, restore takes 95 minutes
  recovery point: 13:30 of work lost, about 162 orders at 12 an hour
  recovery time: 01:55 until the shop is back
  with an hourly backup the recovery point is 00:30 and about 6 orders; the recovery time is the same
  a backup holds every customer's data, so it is sealed with AES-256-GCM
  the archive shows a customer name: false
  the right key opens it: true
  another key: refused
  the same archive offered as the next night's: refused, because its name is sealed in with it
  the key file has permissions rw-------, and lives apart from the backups
  a lost key is a lost backup, so the key needs its own safe copy
