ONE. Deny by default: every path needs a rule.
  THE RULES (in Shop.chain, checked top to bottom):
    GET /orders       needs orders:read
    GET /reports      needs reports:read
    GET /secrets      needs secrets:read
    GET /staff/**     needs the role SUPPORT
    PUT /payments/**  needs payments:write, or a grant
    /refunds/**       signed in; the methods decide
    anything else     denyAll
  THE REQUESTS:
    1  no credentials         GET /orders
    2  alice, wrong password  GET /orders
    3  alice (support)        GET /orders
    4  alice (support)        GET /reports
    5  dave (admin)           GET /admin/debug
  THE RESPONSES:
    1  401  who are you?
    2  401  wrong password, so still unknown
    3  200  she holds orders:read
    4  403  known, but no reports:read
    5  403  no rule matches, so denyAll  <- EVEN FOR AN ADMIN
  401: not signed in.  403: signed in, but not allowed.
TWO. Method security: the rule sits next to the code it guards.
  THE RULES ON THE METHODS (in Refunds):
    create()  @PreAuthorize   needs refunds:create
    view()    @PostAuthorize  requester, or refunds:approve
  THE REQUESTS:
    1  bob (warehouse)  POST /refunds
    2  alice (support)  POST /refunds
    3  alice            GET /refunds/R-1
    4  carol (finance)  GET /refunds/R-1
    5  bob              GET /refunds/R-1
  THE RESPONSES:
    1  403  no refunds:create, so create() never ran
    2  200  the new refund is R-1
    3  200  her own request
    4  200  an approver may read any
    5  403  someone else's request
  did view() run for bob before his 403? true
  <- @PostAuthorize RUNS FIRST: NO SIDE EFFECTS
THREE. Separation of duties: two people for a refund.
  THE RULE ON approve() (in Refunds):
    hasAuthority('refunds:approve')
    and @refundRules.differentPerson(#id, authentication)
  THE REQUESTS:
    1  alice (support)  approves her own R-1
    2  dave (admin)     creates R-2, then approves it
    3  carol (finance)  approves R-1, alice's
    4  dave (admin)     approves R-3, which alice created
  THE RESPONSES:
    1  403  no refunds:approve
    2  403  same person  <- ADMIN POWER DOES NOT HELP
    3  200  approved by carol
    4  200  approved by dave: someone else's request
  the rule is one bean the annotation calls: no role turns it off
FOUR. A role hierarchy, and what a stolen credential can reach.
  THE HIERARCHY: ADMIN includes SUPPORT, FINANCE and WAREHOUSE
  GET /staff/queue NEEDS THE ROLE SUPPORT:
    alice (SUPPORT)      200
    dave (ADMIN)         200  ADMIN includes SUPPORT
    carol (FINANCE)      403
    exporter (EXPORTER)  403
  BEFORE THE FIX (the nightly export runs as dave, the admin):
    a stolen token reaches 15 of 15  <- EVERYTHING
  AFTER THE FIX (the exporter service account):
    it holds orders:read reports:read
    a stolen token reaches 2 of 15
    GET /orders: 200, GET /secrets: 403
  the others: alice 3 of 15, bob 3, carol 3
  each count asks Spring Security's own authorization manager
FIVE. Access that expires by itself.
  THE GRANT (for a month-end fix):
    carol (finance) gets payments:write
    from tick 10 to tick 12, both included
  THE REQUESTS AND RESPONSES (PUT /payments/P-1):
    tick 9   carol  403  before the grant
    tick 10  carol  200  inside the grant
    tick 12  carol  200  inside the grant
    tick 13  carol  403  expired by itself
    tick 11  alice  403  never had a grant
  GrantAuthorization asks a clock the tests can set
