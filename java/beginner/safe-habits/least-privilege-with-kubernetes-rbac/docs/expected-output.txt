ONE. The nightly export job that was given cluster-admin.
  the shop's namespace has 56 things a token could be used for: 7 verbs on 8 kinds of object
  if the nightly-export-admin token is stolen it reaches 56 of 56  <- THE WHOLE NAMESPACE, AND THE WHOLE CLUSTER
  if the exporter token is stolen it reaches 2 of 56: get and list pods (one named config map is also readable, and is not counted)
  the exporter can read the config map export-settings: true
  the exporter can read another config map, payment-keys: false
  the exporter can read secrets: false
TWO. The wildcard trap: "read everything".
  the reporter's role says get and list on all resources, which sounds read-only and harmless
  the reporter can read secrets: true  <- EVERY PASSWORD AND KEY IN THE NAMESPACE
  the reporter can change anything: false
  the reporter reaches 16 of 56, but "everything" includes things that did not exist when the role was written
  a rule that names its resources keeps meaning what it said, and a rule with resourceNames names the objects as well
THREE. Ways to become more powerful than you were given.
  exporter: 0 escalation paths
  ci-deployer: 4 escalation paths
    can create pods, which can mount any secret or service account token in the namespace
    can create role bindings
    can bind roles it does not hold
    can edit roles to add permissions it does not hold
  the deploy pipeline can read secrets directly: false, and it can create a pod that mounts them: true
  so "create pods" is as powerful as "read secrets", and "bind" or "escalate" is as powerful as owning the namespace
FOUR. A cluster-wide role through a namespaced binding.
  the role shop-viewer is a ClusterRole, and the support agent holds it through a RoleBinding in the shop namespace
  the support agent can list pods in shop: true
  the support agent can list pods in warehouse: false
  the support agent can delete pods in shop: false
  the cluster-admin job can list pods in warehouse: true  <- A CLUSTER BINDING IGNORES NAMESPACES
  the binding decides the reach, not the role: a role can be shared, a binding is where the scope is set
FIVE. A linter for the habits that cause incidents.
  findings in the shop manifests: 6
    nightly-export-is-admin: binds cluster-admin
    report-reader: wildcard resources
    deployer: escalation verb escalate
    deployer: escalation verb bind
    default: token is mounted into every pod
    nightly-export-admin: token is mounted into every pod
  a linter finds wildcards and cluster-admin, not a role that is too wide but spelled out in full
  ask the cluster too: kubectl auth can-i --list --as=system:serviceaccount:shop:exporter -n shop
