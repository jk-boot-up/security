ONE. Policies written as code.
  the store's account offers 25 things to do: an action on a resource, such as reading one report or querying one table
  policy wildcard: 1 statement(s), so an identity wearing it can do 25 of 25
  policy exporter: 3 statement(s), so an identity wearing it can do 3 of 25
  policy deployer: 2 statement(s), so an identity wearing it can do 3 of 25
  the number of things an identity can do if its key is stolen is its blast radius
  the nightly export needs 3 of them, and the shortcut policy gives 25
TWO. How a request is matched.
  exporter reads a report file: ALLOW
  exporter reads a secret file: IMPLICIT_DENY
  exporter lists the reports bucket: ALLOW
  exporter lists using a file's name instead of the bucket's: IMPLICIT_DENY
  exporter reads the bucket itself as if it were a file: IMPLICIT_DENY  <- /* means the contents, not the bucket
  action names ignore case, s3:getobject: ALLOW
  the pattern s3:Get* matches s3:GetObject: true, and s3:PutObject: false
  anything not allowed is denied by default
THREE. A deny beats every allow.
  admin with a deny on secrets can do 20 of 25, against 25 without the deny
  reading the secret file: EXPLICIT_DENY
  writing a report: ALLOW
  with the statements in the opposite order the answer is the same: true
  the deny is a safety net, and it still leaves 20 things open
FOUR. A permissions boundary.
  the wildcard policy alone: 25 of 25
  the same policy under the boundary: 8 of 25
  the boundary alone, with nothing attached to the identity: 0 of 25  <- A BOUNDARY GRANTS NOTHING
  admin with a deny, under the boundary: 8 of 25
  an identity gets only what both its policies and its boundary allow
FIVE. A linter, and the way to more power.
  wildcard: 2 finding(s) (ACTION_STAR 1, RESOURCE_STAR 1)
  exporter: 0 finding(s)
  admin_with_deny: 2 finding(s) (ACTION_STAR 1, RESOURCE_STAR 1)
  boundary: 1 finding(s) (RESOURCE_STAR 1)
  deployer: 2 finding(s) (RESOURCE_STAR 1, ESCALATION 1)
  deployer can do only 3 of 25, and is still dangerous: iam:PassRole on every role plus lambda:CreateFunction runs code as any role in the account
  the count hides escalation, so read the policy as well as counting it
  this evaluator ignores conditions, resource policies and organisation rules, and refuses a statement with a condition: true
