ONE. Versioning: an overwrite does not destroy the old data.
  the shop stores orders.csv, then ransomware overwrites it with scrambled bytes
  versions kept for orders.csv: 2
  what a normal read returns now is the scrambled file: true
  the original is still there as an older version: true
  restore = write the older version back as the newest: true
  the scrambled version is still in the history as evidence: true
  a plain delete only adds a delete marker (1): reading the key now fails, the data is not gone: true
  but an attacker with delete rights on versions can still remove every version, which is what the next act stops
TWO. Object Lock: nobody can delete a locked version, not even the root account.
  a backup is stored with COMPLIANCE retention for a day
  delete that version: refused (403 AccessDenied)
  delete it asking to bypass governance: refused (403 AccessDenied)
  shorten the retention: refused (403 AccessDenied)
  a plain delete is allowed but only adds a marker: allowed
  the locked version is still readable: true
  GOVERNANCE is softer. Delete that version: refused (403 AccessDenied)
  with the special bypass permission it can be lifted: allowed
  COMPLIANCE cannot be lifted by anyone until the date, so choose it with care
THREE. The backup job gets its own identity that can only add objects.
  the backup job writes a backup: allowed
  it tries to read one back: refused (403 AccessDenied)
  it tries to list versions: refused (403 AccessDenied)
  it tries to delete: refused (403 AccessDenied)
  it tries to delete a version: refused (403 AccessDenied)
  it tries to write to the orders bucket: refused (403 AccessDenied)
  so a thief who steals the backup job's key can add data but cannot read, change history or destroy backups
  it can still add junk, so the quota and the alerts on unusual uploads matter
FOUR. A checksum catches a backup damaged on the way.
  upload with the SHA-256 of the data: allowed
  upload bytes whose SHA-256 does not match the one sent: refused (400 BadDigest)
  what was stored for the good upload hashes to the same value: true
  the damaged upload left nothing behind: true
  the store checks bytes in transit and at upload; a restore test is still needed to know the backup is usable
FIVE. Keeping history without keeping it for ever, and the cost.
  a lifecycle rule on the orders bucket: 1 rule, expire-old-versions, removes old versions 30 days after they are replaced
  every version is stored in full, so storage grows with every overwrite until the rule removes them
  a COMPLIANCE lock cannot be undone, so a mistaken retention date is paid for in storage
  the root account is the real key: whoever holds it can change policies and users, so keep it out of daily use
  object lock stops the API from deleting backups; it does not stop someone from deleting the disks, so keep a copy somewhere else too
