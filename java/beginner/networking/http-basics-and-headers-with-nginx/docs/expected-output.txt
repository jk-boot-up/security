ONE. nginx in front of the shop, as it comes.
  GET / answers 200 and scores 0 of 5 on the security headers
  the Server header shows the exact nginx version: yes  <- A FREE HINT FOR AN ATTACKER
TWO. add_header, and the word always.
  headers added without always: GET / scores 5 of 5, but the 404 page scores 0 of 5  <- ERROR PAGES ARE LEFT BARE
  headers added with always: GET / scores 5 of 5 and the 404 page scores 5 of 5
  with server_tokens off the Server header is just: nginx
THREE. The inheritance trap.
  headers set once for the whole server: GET / scores 5 of 5
  /account adds its own Cache-Control header, and now scores 0 of 5  <- ITS OWN add_header DROPPED THE REST
  Cache-Control is there: yes
  with the five headers repeated inside /account it scores 5 of 5
  the habit: audit every location, not just the top of the page
FOUR. Limits, and requests that are ambiguous.
  client_max_body_size 1k: a 100 byte order gets 200, a 2000 byte order gets 413
  large_client_header_buffers 2 1k: a header line of 4000 characters gets 400
  Content-Length and Transfer-Encoding together, the smuggling pattern: 400
  two different Content-Length headers: 400
  nginx refuses both, so it cannot disagree with the application behind it about where a request ends
FIVE. Hiding what the application gives away, and the bill.
  the application behind the proxy sends X-Powered-By and X-AspNet-Version: yes  <- OLD VERSIONS HAVE KNOWN HOLES
  with proxy_hide_header and server_tokens off, extra headers left: 0, Server says: nginx
  hiding is a speed bump, not a lock: the real fix is to keep the software up to date
  the bill: the configuration is easy to get subtly wrong, so test it, as these demos do
  and the headers describe the page, so a Content-Security-Policy still has to match the real site
