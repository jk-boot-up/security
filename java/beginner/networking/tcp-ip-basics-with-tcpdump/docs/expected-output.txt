ONE. Recording traffic to a capture file.
  a customer's purchase is 5 packets, 234 bytes
  in a pcap file it is 24 bytes of file header, then 16 bytes of header and the packet bytes for each packet: 338 bytes
  tcpdump, Wireshark and the Python script all read the same file
TWO. Reading it back, in the style of tcpdump.
  IP 198.51.100.7.51000 > 203.0.113.10.443: Flags [S], seq 1000, win 65535, length 0
  IP 203.0.113.10.443 > 198.51.100.7.51000: Flags [S.], seq 7000, ack 1001, win 65535, length 0
  IP 198.51.100.7.51000 > 203.0.113.10.443: Flags [.], ack 7001, win 65535, length 0
  IP 198.51.100.7.51000 > 203.0.113.10.443: Flags [P.], seq 1001:1035, ack 7001, win 65535, length 34
  IP 203.0.113.10.443 > 198.51.100.7.51000: Flags [.], ack 1035, win 65535, length 0
  S is SYN, a dot is ACK, P is PSH: the handshake is the first three lines, and the order is the fourth
THREE. Finding a SYN flood in a capture.
  the capture has 14 packets: the purchase, then 8 SYNs from addresses that never answer, then one more
  sources that sent a SYN and never finished the handshake: 9
  the real customer is among them: false
  the first of them is 100.64.0.1 and they are all from the same network, which is what a flood often looks like
FOUR. Finding a damaged packet.
  packets whose checksum does not match: 1
  tcpdump without -v shows it like any other; with -v it marks the checksum incorrect
  a capture shows what arrived, damaged or forged, which is why it is the first thing to look at
FIVE. What a capture reveals.
  the capture contains the card number: true  <- A CAPTURE FILE IS AS SENSITIVE AS THE TRAFFIC
  so protect capture files like passwords, and capture only what the investigation needs
  live capture needs root, so analyse recorded files without it, on a copy
  encryption with TLS is what makes a capture useless to a thief
