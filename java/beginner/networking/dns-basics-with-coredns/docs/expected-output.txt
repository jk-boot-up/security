ONE. A real DNS server, in a container.
  the zone file for shop.example says www.shop.example is 203.0.113.10 for 300 seconds
  asked over UDP, CoreDNS answers www.shop.example is 203.0.113.10
  the answer repeats the question's id: true, and says it is a response: true
  the client trusts it because the id and the question match, and nothing else
  THE QUESTION (what the client sends over UDP, 34 bytes):
    id         10 01        picked by the client
    flags      01 00        a question, recursion desired
    counts     00 01 00 00  1 question, 0 answers
               00 00 00 00  0 other records
    name       03 www 04 shop 07 example 00
    type       00 01        A: an IPv4 address
    class      00 01        IN: internet
  THE ANSWER (as DnsMessage writes it, 50 bytes):
    id         10 01        the question's id, repeated
    flags      81 80        a response, no error
    counts     00 01 00 01  1 question, 1 answer
               00 00 00 00  0 other records
    question   the same 22 bytes
    name       c0 0c        points back to byte 12
    type+class 00 01 00 01  A, IN
    ttl        00 00 01 2c  300 seconds
    length     00 04        4 bytes follow
    address    cb 00 71 0a  203.0.113.10
TWO. The same question over UDP and over TCP.
  both give the same address: true
  over TCP each message starts with its length in two bytes, so the answer is 2 bytes longer
  TCP is used when an answer does not fit in a datagram, and to copy a whole zone between servers
  neither one signs or encrypts anything
THREE. Names that do not exist, names it will not answer, and a rewrite.
  nope.shop.example: NXDOMAIN with 0 answers
  www.other.example: REFUSED, because this server only answers for shop.example
  legacy.shop.example is rewritten to www.shop.example and the answer is 203.0.113.10 under the name asked for: legacy.shop.example
  a rewrite is a rule in the server, invisible to the client
FOUR. The cache and the countdown of the time to live.
  the cache plugin keeps answers for at most 60 seconds, so the zone's 300 is cut to 60: true
  each answer from the cache has a smaller time to live than the one before: true
  the first answer, from the zone file, was not counted down: true
  a cache makes DNS fast, and keeps a false answer until its time runs out
FIVE. A zone with a wrong record.
  someone changes the record for www.shop.example to 192.0.2.66 with a time to live of 86400 seconds
  CoreDNS serves it exactly as it serves the right one: 192.0.2.66  <- THE SERVER CANNOT TELL
  the cache setting cuts the 86400 seconds to 60 in what it hands out: true, but a resolver that does not cap would keep it for a day
  fixing the file fixes the server, but every resolver that cached the wrong answer keeps it until its time runs out
  the defences are around the file: who may change it, review of changes, a short time to live for important names
  DNSSEC lets a resolver see a record forged on the way, but it signs whatever is in the zone, wrong records too (described, not run)
