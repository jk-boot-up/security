Spring Security answers who is asking with a login filter and a password encoder, and what they may do with rules on the endpoints, and a forgotten rule is still an open door.

This project teaches the same two questions as the plain version, authentication (who are you?) and authorization (what may you do?), but with a framework doing the work. Spring Security puts a chain of filters in front of the application. One filter reads the username and password. A password encoder checks them against a stored BCrypt hash. If nobody is known, the chain answers 401. Rules written on the endpoints, such as @PreAuthorize, decide what a known person may do, and a refusal is a 403.

The demo runs the real filter chain through Spring's MockMvc, so there is no web server and no network port. The online store, its four people and the five acts are the same as in the plain project, so the two can be compared side by side.

The idea in everyday terms

Think of a hotel again, now with a security desk at the door. The desk checks every guest's passport (the authentication filter), and a key-card system holds the rules for who may open which door (the authorization rules). You still run the hotel. The framework simply makes sure nobody walks past the desk, and that every door asks the key-card system.

The scenario

The online store has customers Ana and Ben, support staff Sam and an admin Alex. Version one has Spring Security installed but permits everything. Version two requires a login and nothing else, so a signed-in customer can still refund any order. Version three adds @PreAuthorize rules to the endpoints. A last act shows two costs: an endpoint whose rule was forgotten is open to every signed-in user, and HTTP Basic checks the password on every single request.

Run

./gradlew run

The demo tells the story in 5 acts, each printing exact numbers that the tests check:

Act What it shows
1. Spring Security present, but every request permitted With the filter chain set to permit everything, anyone can refund and view any order.
2. Authentication: HTTP Basic, passwords stored as BCrypt No credentials or a wrong password get a 401; the right password gets 200; stored passwords start with the BCrypt marker.
3. Authenticated is not the same as authorized With the login rule and nothing else, a customer can refund orders and read other people's orders.
4. Authorization: @PreAuthorize rules on the endpoints Rules on the methods decide: no credentials get 401, a customer who may not gets 403, support and admins get what their role allows.
5. The bill: a forgotten rule, and a password check on every request An endpoint without its annotation is open to every signed-in user; a rule on the address closes it; HTTP Basic checks the password on all 3 requests.

Test

./gradlew test

13 tests in BillTest, DemoRunsTest, FilterChainTest. Every line the demo prints is checked against docs/expected-output.txt, the filter chain runs in the same JVM with no network, and BCrypt hashes are only compared, never printed in full, so every run gives the same result.

What the simulation got right, and what it left out

The demo does not start a web server. MockMvc sends requests straight through the filter chain and the dispatcher, so the results are the ones a real server would give, and the run is fast and repeatable. HTTP Basic without a session is used because it keeps each request self-contained; real browsers more often use a login form and a session cookie. CSRF protection is switched off in the demo's configuration to keep the code short, and must stay on for any application that uses cookies. The BCrypt cost is 4, the lowest allowed, for speed; real systems use 10 or more.

What it costs

  • A forgotten rule is an open endpoint. @PreAuthorize protects only the methods that carry it. A rule on the address as a second layer catches the ones that forget.
  • HTTP Basic checks the password on every request. BCrypt is slow on purpose, so every call pays for it. Sessions or tokens avoid this, at the cost of managing them.
  • Framework configuration is code to review. The chain, the matchers and the order of the rules are as important as the rules themselves, and a mistake there is silent.
  • A dependency to keep up to date. Security fixes arrive through new Spring Security versions, and falling behind is a risk of its own.

When this is too much

For a tiny internal tool with a single shared password, the framework is more than the problem needs. For anything with accounts and different rights, a framework's tested filters and password handling are better than writing your own, which is why the plain project exists to teach the ideas and this one to show how they are normally applied.

Where you have already met this

  • The @PreAuthorize, @Secured and hasRole(...) annotations in almost every Spring application.
  • A SecurityFilterChain bean, and the authorizeHttpRequests block inside it.
  • The {bcrypt} prefix in stored passwords of Spring applications.
  • The browser's built-in sign-in box, which is HTTP Basic.
