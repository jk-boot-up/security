ONE. A password alone.
  an attacker has dana's password from another site's breach
  the attacker logs in: OK  <- ONE FACTOR, ONE LEAK
TWO. Enrolling a second factor.
  the bank makes a 20-byte secret and shows it as Base32: GEZDGNBVGY3TQOJQGEZDGNBVGY3TQOJQ
  at time 59 the counter is 1 and the code is 287082
  the code for steps 0 to 3, each lasting 30 seconds: 755224, 287082, 359152, 969429
  the phone and the bank each work it out from the secret and the time, and never talk
THREE. Logging in with a code, and clocks that disagree.
  the password alone: CODE_NEEDED
  dana's phone shows 287082 at time 59: OK
  a wrong code, 000000: WRONG_CODE
  a phone 25 seconds fast shows 359152: OK (the bank allows 1 step either side)
  a phone 70 seconds fast shows 338314: WRONG_CODE (3 steps ahead)
  an old code, from step 2, used at time 120 (step 4): WRONG_CODE
FOUR. The same code twice.
  without replay protection: dana logs in with 287082: OK; an observer uses it 5 seconds later: OK  <- REPLAY
  with replay protection: dana logs in with 287082: OK; an observer uses it 5 seconds later: REPLAYED
FIVE. The bill: what a code cannot do.
  dana types her password and code 287082 into a fake bank page, which passes both on at once: OK  <- CANNOT TELL THE FAKE PAGE FROM THE REAL ONE
  the bank's table is stolen, and it holds the secret: the attacker's own app shows 287082 at time 59, the same as dana's  <- THE SECRET LIVES ON THE SERVER TOO
  dana loses her phone and uses a recovery code: OK
  the same recovery code again: WRONG_CODE
  a recovery code is a second way in, so it must be guarded like the password
