ONE. The library makes the same codes as the hand-written version.
  codes for steps 0 to 3, at times 0, 30, 60 and 90: 755224, 287082, 359152, 969429
  at time 59 the code is 287082  <- THE VALUE IN RFC 4226 AND 6238
TWO. What the library checks, and what it leaves to the bank.
  the library says 287082 is right at time 59, in step 1: true
  the library says 287082 is right at time 40, also step 1: true
  the library says 287082 is right at time 65, in step 2: false  <- ONE STEP ONLY
  the bank's own window of 1 accepts it at time 65: OK
  and refuses it two steps on, at time 95, in step 3: WRONG_CODE
THREE. Other hashes and longer codes.
  SHA-1, 8 digits, at time 59: 94287082
  SHA-256, 8 digits, at time 59: 46119246
  SHA-512, 8 digits, at time 59: 90693936
  all three are the values of RFC 6238
  some authenticator apps ignore these settings and use SHA-1, 6 digits, 30 seconds
FOUR. Giving the secret to the phone.
  the QR code carries this text:
  otpauth://totp/Example%20Bank:dana%40example.com?secret=GEZDGNBVGY3TQOJQGEZDGNBVGY3TQOJQ&issuer=Example%20Bank&algorithm=SHA1&digits=6&period=30
  the app reads it once and keeps the secret, which is why the screen must be private
FIVE. The bill: what the library does not do.
  the library alone, the same code twice: OK, OK  <- NOT THE LIBRARY'S JOB
  with the bank's own memory of the last step: OK, REPLAYED
  the library keeps no secrets, counts no wrong codes and limits no attempts
  those, and the choice of window, are the bank's to write and to test
