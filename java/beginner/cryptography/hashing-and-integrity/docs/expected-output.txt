ONE. A checksum for accidents.
  invoice INV-1001|ana|Laptop|1200 has CRC-32 a7c21715
  one bit flips on the disk: the CRC is now d0c52783  <- ACCIDENT DETECTED
  an attacker changes the amount to 12 and works out a new CRC, 5e22dd78  <- THE CHECK PASSES
  a CRC has no secret, so it only guards against accidents
TWO. A cryptographic hash: SHA-256.
  SHA-256 of the three letters abc begins ba7816bf8f01
  invoice at 1200 dollars begins 878229813e30
  invoice at 1201 dollars begins 7da712a12a1c
  one digit changed, and 62 of the 64 hex digits differ
  that is 134 of 256 bits: about half, whatever the input
  the hash is always 64 hex digits, for one line or for a whole book
THREE. A hash kept beside the data.
  an attacker changes the invoice to 12 dollars, and leaves the hash: intact? false
  an attacker changes the invoice and the hash beside it: intact? true  <- THE ATTACKER WROTE BOTH
  the shop publishes the installer's hash on its own site, over HTTPS: 891124db5651
  a download from a mirror hashes to 70fa24395df6: refused  <- THE HASH CAME BY ANOTHER ROAD
FOUR. A keyed hash: HMAC-SHA-256.
  the order service tags invoice INV-1001: 54916ce11158
  the invoice with its tag: OK
  an attacker changes the amount, keeps the tag: BAD_TAG
  the attacker tags it with a plain SHA-256 instead: BAD_TAG
  the attacker tags it with HMAC and a guessed key: BAD_TAG
  without the key, no tag the service accepts can be made
FIVE. The bill: boundaries, repeats, and a shared key.
  fields joined with nothing between: (ab, c) and (a, bc) get tags e120bc23dcb2 and e120bc23dcb2
  the attacker moves a field boundary, keeping the tag: OK  <- THE BOUNDARY MOVED
  with each field's length in front: BAD_TAG
  a valid invoice is sent twice: OK, OK  <- A TAG DOES NOT SAY WHEN
  when the service remembers invoice numbers: OK, REPLAYED
  the warehouse holds the same key to check tags, and can make one: OK  <- KEY HOLDERS CANNOT BE TOLD APART
  to prove who made a tag, a signature with a private key is needed: the next projects
