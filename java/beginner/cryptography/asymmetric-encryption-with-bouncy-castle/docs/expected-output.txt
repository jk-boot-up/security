ONE. Keys as PEM text.
  Ana's public key as text begins: -----BEGIN PUBLIC KEY-----
  her private key as text begins: -----BEGIN PRIVATE KEY-----  <- ANYONE WHO READS THE FILE HAS THE KEY
  the public key reads back to the same key: true
  encrypted with a password it begins: -----BEGIN ENCRYPTED PRIVATE KEY-----
  with the right password it reads back: true
  with a wrong password: refused
TWO. A certificate for the public key.
  subject: CN=Ana,O=Example Bank customer
  valid from 2026-01-01T00:00:00Z to 2027-01-01T00:00:00Z
  signed with SHA256WITHRSA
  issuer equals subject: true  <- ANYONE CAN MAKE ONE, SO IT PROVES NOTHING YET
  the certificate as text begins: -----BEGIN CERTIFICATE-----
THREE. A standard envelope: CMS EnvelopedData.
  the bank seals a 10000-byte statement for Ana's certificate: AES-256 for the data, RSA-OAEP for the key
  Ana opens it: true
  Eve tries her own private key: refused
FOUR. A different program opens it.
  the openssl command-line tool, written by other people, is given the envelope, the key file and the certificate
  it opens the statement: true  <- A REAL STANDARD, NOT ONLY THIS LIBRARY
FIVE. The bill: what Bouncy Castle costs.
  the envelope above locks the key with RSA-OAEP (1.2.840.113549.1.1.7)
  the simple call that most examples show locks it with RSA with PKCS#1 v1.5 padding (1.2.840.113549.1.1.1)  <- THE EASY CALL PICKS THE OLDER PADDING
  the library is about 7 MB, and registering it changes every library in the program
  its package names changed from jdk15on to jdk18on, so upgrades need care
  the JDK alone could do the maths, but not the PEM, the certificate or the CMS format
