ONE. A chain built with Bouncy Castle.
  BEFORE BUILDING (what each builder is asked for):
    root          a CA, 1 more CA below, self-signed
    intermediate  a CA, 0 below, only names under shop.example
    server        not a CA, for shop.example, to sign data
  AFTER BUILDING (read back from the certificates):
    root          CN=Example Root CA, CAs below: 1
    intermediate  CN=Example Issuing CA, CAs below: 0
                  name rule: shop.example
    server        CN=shop.example, a CA: false
  KEY USAGE, BIT BY BIT (0 data, 5 certificates, 6 lists):
    intermediate  000001100  signs certificates and lists
    server        100000000  signs data only
  each names its parent's key identifier: true, true
TWO. A limit the authority carries in its own certificate.
  BEFORE THE CHECK (the intermediate's rule: shop.example):
    shop.example, api.shop.example, other.example
  STEP. THE RULE BY HAND (the name, or ending in .shop.example):
    shop.example       the same name: true
    api.shop.example   ends with .shop.example: true
    other.example      neither: false
    evilshop.example   neither: false
  AFTER THE CHECK (the JDK's PKIX, given each chain):
    shop.example       accepted true
    api.shop.example   accepted true
    other.example      accepted false, INVALID_NAME
  a stolen intermediate key can sign only names under shop.example
THREE. A revocation list signed by the issuer.
  BEFORE REVOCATION (the intermediate's signed list):
    entries 0, the chain accepted: true
  AFTER REVOCATION (the shop's key is lost):
    entries 1: serial 3, KEY_COMPROMISE
    signed by the intermediate: true, by the root: false
    the chain accepted: false, REVOKED
  WITHOUT A GOOD LIST (accepted, and the reason):
    a stranger's list  false, UNDETERMINED_REVOCATION_STATUS
    no list at all     false, UNDETERMINED_REVOCATION_STATUS
  this client refuses when it cannot find out; many browsers
  go ahead instead, which is why short-lived certificates matter
FOUR. Asking for a certificate without handing over the private key.
  THE REQUEST (signed by the shop; the private key stays home):
    names [shop.example], public key EC
    the signature proves the sender holds the key: true
    one letter changed on the way, it still proves it: false
  THE RESPONSE (the authority's policy: names under shop.example):
    shop.example: signed, serial 10, holds the shop's key: true
    bank.example: refused, bank.example is outside shop.example
  as PEM: -----BEGIN CERTIFICATE-----, reads back the same: true
FIVE. A stolen authority key, and the bill.
  BEFORE REVOCATION (a thief has the intermediate's private key):
    the thief signs shop.example, serial 77
    the forged chain accepted: true  <- EVERYTHING BELOW FALLS
  AFTER REVOCATION (the root's list: serial 2, CA_COMPROMISE):
    the forged chain accepted: false
    the shop's real chain accepted: false
    so the shop needs a new certificate from a new intermediate
  THE BILL:
    revocation protects only clients with the new list
    builders are short to write and easy to get subtly wrong:
    a missing critical flag or constraint weakens a rule
    a trusted root may vouch for any name: keep the store small
    and keep CA keys offline or in hardware
