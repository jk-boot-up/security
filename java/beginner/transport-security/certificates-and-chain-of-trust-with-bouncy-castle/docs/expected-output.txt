ONE. A chain built with Bouncy Castle.
  root:         CN=Example Root CA, self-signed: true, authorities allowed below it: 1
  intermediate: CN=Example Issuing CA, authorities allowed below it: 0
  server:       CN=shop.example, may issue certificates: false
  an authority's key may sign certificates and lists: true, and may not sign data: true
  the server's key may sign data: true, and may not sign certificates: true
  each certificate names its parent's key identifier: server to intermediate true, intermediate to root true
  the server certificate names shop.example: true
  the library wrote the extensions from named builders; no byte of the encoding was written by hand
TWO. A limit the authority carries in its own certificate.
  the intermediate may only certify shop.example and names below it (a name constraint)
  the certificate for shop.example: accepted true
  a certificate for api.shop.example from the same intermediate: accepted true
  a certificate for other.example from the same intermediate: accepted false, reason INVALID_NAME
  the limit is checked by the client, so a stolen intermediate key can only be misused for the names it was limited to
THREE. A revocation list signed by the issuer.
  the issuer publishes a signed list; it names 0 revoked certificates and the chain is accepted: true
  the shop's key is lost, so the intermediate lists its serial number (1 entry): accepted false, reason REVOKED
  the list's signature verifies with the intermediate's key: true, with the root's key: false
  a list signed by someone else is not used: accepted false, reason UNDETERMINED_REVOCATION_STATUS
  no list at all: accepted false, reason UNDETERMINED_REVOCATION_STATUS
  this client refuses when it cannot find out; many browsers go ahead instead, which is why short-lived certificates matter
FOUR. Asking for a certificate without handing over the private key.
  the shop makes its own key pair and signs a request naming [shop.example]; the private key stays with the shop
  the request's signature proves the sender holds the private key: true
  one letter of the name changed on the way: the signature still proves possession: false
  the authority's policy allows names under shop.example, so it signs: the certificate holds the shop's public key: true
  a request for bank.example: refused (bank.example is outside shop.example)
  as PEM text it starts with -----BEGIN CERTIFICATE----- and reads back as the same certificate: true
FIVE. A stolen authority key, and the bill.
  someone steals the intermediate's private key and signs their own certificate for shop.example
  the forged chain is accepted: true  <- A STOLEN CA KEY BREAKS EVERYTHING BELOW IT
  the root lists the intermediate as compromised: the forged chain accepted false, the shop's real chain accepted false
  so the shop needs a new certificate from a new intermediate; revocation protects only clients that fetched the new list
  the builders make certificates short to write and easy to get subtly wrong: a missing critical flag or constraint silently weakens a rule
  trusting a root is a decision: it may vouch for any name, so keep the store small and keep authority keys offline or in hardware
