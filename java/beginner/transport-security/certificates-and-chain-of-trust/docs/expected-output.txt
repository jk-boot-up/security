ONE. A chain of three certificates.
  BEFORE SIGNING (what the shop asks for):
    name        CN=shop.example, for the site shop.example
    public key  EC, 256 bits, the shop's own
    valid       2025-06-01 to 2026-06-01
  AFTER SIGNING (the certificate, serial 3):
    the same three, and issuer  CN=Example Issuing CA
    signature   SHA256withECDSA, by the issuer's private key
    anyone checks it with the issuer's public key: true
  THE CHAIN, FROM THE ROOT DOWN:
    root          Example Root CA     self-signed: true
    intermediate  Example Issuing CA  CA: true, by the root
    server        shop.example        CA: false, by the intermediate
TWO. The browser's check, step by step.
  BEFORE THE CHECK (what the browser has):
    sent by the server  shop.example, Example Issuing CA
    already trusted     Example Root CA
    visiting            shop.example, on 2026-01-01
  STEP 1. shop.example AGAINST Example Issuing CA:
    names it as the issuer: true
    its signature checks with that public key: true
    2026-01-01 is in 2025-06-01 to 2026-06-01: true
  STEP 2. Example Issuing CA AGAINST Example Root CA:
    names it as the issuer: true
    its signature checks with that public key: true
    2026-01-01 is in 2025-01-01 to 2030-01-01: true
    it may issue certificates (a CA): true
  STEP 3. THE ROOT AND THE NAME:
    Example Root CA is in the trust store: true
    shop.example is in the certificate: true
  AFTER THE CHECK:
    by hand: accepted true, the JDK: accepted true
    *.example matches shop.example true, a.b.example false
THREE. Three reasons to refuse.
  BEFORE THE CHECK (three chains the browser is shown):
    1. shop.example, valid 2024-01-01 to 2024-12-31
    2. shop.example, from a root also named Example Root CA
    3. the good chain, but the visitor meant evil.example
  AFTER THE CHECK (the failed step, and the JDK's reason):
    1. by hand: the dates       JDK: EXPIRED
    2. by hand: the signature   JDK: INVALID_SIGNATURE
       (the issuer's name matched: true, the key did not)
    3. chain accepted true, the name evil.example matches false
  names prove nothing, only keys do; chain and name are two checks
FOUR. Changed certificates, and certificates that overstep.
  BEFORE THE CHANGE (the signed name):  CN=shop.example
  AFTER THE CHANGE (one letter):        CN=shop.examplE
    it still parses: true
    by hand: the signature   JDK: INVALID_SIGNATURE
  BEFORE THE CHECK (the shop's server key signs other.example):
    the shop's certificate is a CA: false
  AFTER THE CHECK:
    by hand: the CA flag     JDK: INVALID_KEY_USAGE
  the intermediate allows 0 more CAs below it (path length)
FIVE. Revocation, and the bill.
  BEFORE REVOCATION (a thief has the intermediate's private key):
    the thief issues shop.example, serial 77
    the forged chain accepted: true  <- EVERYTHING BELOW FALLS
  AFTER REVOCATION (serials on the client's list):
    serial 3 (the shop's)
       the shop's chain accepted false, REVOKED
    serial 2 (the intermediate's)
       the shop's chain accepted false, the forged false
  THE BILL:
    a list works only if the client has the latest one:
    real clients use CRLs, OCSP, short lifetimes, or all three
    a trusted root may vouch for any name: keep the store small
    and keep CA keys offline or in hardware
