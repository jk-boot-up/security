ONE. A sniffer on the wire, without and with TLS.
  BEFORE TLS (the order, as the sniffer sees it):
    card=4111111111111111&order=A-1001
    34 bytes, the card number readable: true  <- READABLE
  AFTER TLS (one record of 72 bytes, as the sniffer sees it):
    header    17 03 03 00 43  (in the clear)
    the rest  67 bytes, encrypted
    the card number readable: false
  HOW THE 72 BYTES ARE MADE:
    17        type 23, application data
    03 03     version, written as TLS 1.2 for old boxes
    00 43     length: 67 bytes follow the header
    67 bytes  34 order + 1 type + 16 padding + 16 tag
TWO. The handshake.
  BEFORE THE KEYS (the two hellos, in the clear):
    client sends  ClientHello, record type 22
    the site name shop.example.test readable: true
    server sends  ServerHello, record type 22
    chosen        TLSv1.3, TLS_AES_256_GCM_SHA384
  AFTER THE KEYS (the rest of the handshake, encrypted):
    record types from the client  22 20 23
    record types from the server  22 20 23 23
    the certificate readable: false  <- ENCRYPTED
    the keys themselves were never sent
  WHAT THE RECORD TYPES MEAN:
    22  handshake, in the clear
    20  change cipher spec, kept only for old boxes
    23  encrypted: the rest of the handshake, then data
  THE CIPHER SUITE, PART BY PART:
    TLS        the protocol
    AES 256    the cipher, with a 256-bit key
    GCM        the mode: encrypts and adds a tag
    SHA384     the hash that makes the keys
THREE. Who is on the other end.
  BEFORE THE HANDSHAKE (what the client knows):
    asks for  shop.example.test
    trusts    one certificate, SHA-256 0ded3842d38b01a7
  AFTER THE HANDSHAKE (three servers answer):
    1. the shop, certificate 0ded3842d38b01a7
       works: true
    2. an impostor, same name, certificate b72122451fcf2531
       works: false  <- NOT TRUSTED
    3. the shop, but the client asked for other.example.test
       works: false  <- THE NAME MUST MATCH
  a name alone proves nothing: the client must trust the certificate
FOUR. Protecting the data.
  BEFORE SENDING (the order):
    card=4111111111111111&order=A-1001
  AFTER SENDING (the record, in two connections):
    the same bytes on the wire both times: false  <- FRESH KEYS
    the server opens it, and gets the order back: true
  BEFORE THE CHECK (an attacker flips one bit):
    byte 36 of 72, xor 01
  AFTER THE CHECK (the server checks the tag):
    refused, (bad_record_mac) Tag mismatch  <- CHANGE SEEN
  fresh keys come from temporary key pairs, made per connection,
  so a stolen server key cannot open recorded traffic
FIVE. Settings, and the bill.
  BEFORE TIGHTENING (a default server):
    client offers TLSv1    works: false  <- OLD VERSIONS ARE OFF
    client offers TLSv1.2  works: true, agreed TLSv1.2
  AFTER TIGHTENING (the server requires TLS 1.3):
    client offers TLSv1.2  works: false
    client offers TLSv1.3  works: true, agreed TLSv1.3
  THE BILL:
    certificates must be obtained, renewed and kept safe
    the handshake costs a round trip and some computing
    TLS protects the connection, not the ends
    the site name and the message sizes still show
