FIVE. A compromised host.
  FIVE THINGS AN ATTACKER ON THE HOST TRIES:
    1  another process, no PIN, opens the token
    2  asks the bank's service to sign 99,999,999.00
    3  code inside the application, no PIN: 500 forged files
    4  the same code, after the application logs out
    5  another process that has learned the PIN
  THE RESULT:
    1  login refused, private keys seen 0
    2  refused: needs two approvers
    3  500 of 500 signed, all verify with the bank's key
       audit entries added 0, chain still verifies yes
    4  old key reference signs no, fresh KeyStore signs no
    5  signs yes, verifies yes
SIX. A key that can be backed up, and the limits.
  THE RELEASE-SIGNING KEY, EXTRACTABLE ON PURPOSE:
    key      EC P-256, made on the token, CKA_EXTRACTABLE true
    wrapped  under a sensitive AES token key (key wrap, padded)
  THE BACKUP CYCLE:
    wrap                CKR_OK, a blob of 80 bytes
    destroy, then sign  CKR_OBJECT_HANDLE_INVALID
    unwrap the blob     CKR_OK, signs yes, verifies yes
  AN ATTACKER WITH A LOGGED-IN SESSION:
    wraps it under a key they can read  CKR_OK
    opens it in Java: 67 key bytes, padded to 72, + 8 = 80
    a forged release signature verifies  yes
  THE WRAPPING KEY LOST WITH THE TOKEN:
    restores the key  no (CKR_UNWRAPPING_KEY_HANDLE_INVALID)
  ---
  WHAT THE TOKEN PROTECTS (ways to copy a key out that worked):
    non-extractable token key  0 of 5
    extractable token key      1 of 1
    key in a file              1 of 1
  WHAT IT DOES NOT PROTECT:
    use while logged in, by anyone in the process  yes
    rate, approvers, audit bypassed from inside    yes
  CLEAN UP:
    token, keystore file and copies removed  yes
