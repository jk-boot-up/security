--- revocation by OCSP: an openssl ocsp responder that is up, down or hanging
hard fail = the client refuses when it cannot learn the status; soft fail = it accepts
good certificate, responder up: hard fail accepted, soft fail accepted
OCSP requests the responder saw for those 2 checks: 2
revoked certificate, responder up: hard fail refused (revoked), soft fail refused (revoked)
good certificate, responder down: hard fail refused (revocation status unknown), soft fail accepted
revoked certificate, responder down: hard fail refused (revocation status unknown), soft fail accepted
revoked certificate, responder hangs: hard fail refused (revocation status unknown), soft fail accepted
each check of the hanging responder waited about 1 second (the demo's timeout; the JDK default is 15): yes
a revoked certificate gets through a soft-fail client whenever the answer can be blocked: yes
--- revocation by CRL: a signed list that the client downloads
CRL signed by the intermediate and verified in Java: yes; entries: 1; good for 3600 seconds in this lab (the entry is the card service certificate revoked above)
the certificate is revoked after that CRL was published; a client holding the old CRL: accepted
new CRL: entries 2; a client holding it: refused (revoked)
client clock 2 hours later, the CRL's next update has passed: hard fail refused (revocation status unknown), soft fail accepted
a revoked certificate stays usable for clients that hold the old list until their next download: up to 3600 seconds in this lab
--- OCSP stapling: the server sends a signed, dated OCSP response inside the TLS handshake (openssl s_server -status_file)
size of the response: under 512 bytes yes
server that staples, responder up: accepted, responses in the handshake 1, requests to the responder 0
server that does not staple, responder up: accepted, responses in the handshake 0, requests to the responder 1 (the responder learns which site the client visits)
server that does not staple, responder down: hard fail refused (revocation status unknown), soft fail accepted
server that staples, responder down: hard fail accepted
same staple read 2 days later, past its next update, responder down: hard fail refused (OCSP response out of date)
certificate revoked, the server still sends the staple made before: accepted, requests to the responder 0
same server, a client that ignores the staple and asks the responder: refused (revoked)
server with a staple made after the revocation: refused (revoked)
a staple moves the question to the server and survives a dead responder; it is as old as its last refresh (1 day in this lab)
--- how big a CRL gets (the CA database is written with this many revoked entries, then openssl ca writes the CRL)
revoked entries 1,000: CRL 20 KB, 21 bytes per entry, a phone at 1 Mbit/s needs 0.2 seconds for it
revoked entries 10,000: CRL 205 KB, 21 bytes per entry, a phone at 1 Mbit/s needs 1.7 seconds for it
revoked entries 100,000: CRL 2120 KB, 22 bytes per entry, a phone at 1 Mbit/s needs 17.4 seconds for it
100,000 revoked entries, 90,000 of them for certificates that have expired, after openssl ca -updatedb: CRL 2120 KB (openssl keeps revoked entries after expiry; -updatedb only marks valid ones)
the same CA if it dropped the 90,000 entries that RFC 5280 lets it drop: CRL 205 KB
a CA that drops expired entries keeps the list as long as the lifetimes of the certificates on it: short lifetimes, short lists

--- the bill
revocation is a question that needs an answer: with hard fail a dead responder is an outage, with soft fail it is a bypass
a CRL is big and old, an OCSP answer is small and live but must be asked for, a staple is small and moves the ask to the server
a short life makes revocation almost unnecessary and turns renewal into the thing that must never fail
the headroom for a CA outage is a third of the life; a monitor that counts the days left is the last line
