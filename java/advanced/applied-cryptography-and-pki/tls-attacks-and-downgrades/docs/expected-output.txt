FOUR. A recorded session, and the server key leaks later.
  THE RECORDING (one session per suite, through a tap):
    request                      the same in each session:
    POST /transfer?from=ACC-1001&to=ACC-2002&amount=2500
    AES128-GCM-SHA256            negotiated yes, in clear: no
    DHE-RSA-AES128-GCM-SHA256    negotiated yes, in clear: no
    ECDHE-RSA-AES128-GCM-SHA256  negotiated yes, in clear: no
  WHAT THE CLIENT SENT IN ITS KEY EXCHANGE MESSAGE:
    static RSA  256 bytes: the secret, encrypted to the key
    DHE         128 bytes: a DH public value only
    ECDHE       32 bytes: an EC public value only
  HOW THE LEAKED KEY OPENS THE STATIC RSA SESSION:
    1 RSA-decrypt the 256 bytes -> pre-master secret, 48 bytes
    2 PRF(pre-master, "master secret", randoms) -> 48 bytes
    3 PRF(master, "key expansion", randoms)   -> 40 bytes
    4 key block bytes 0-15  -> client write key, 16 bytes
    5 key block bytes 32-35 -> client salt, 4 bytes
    6 AES-GCM, nonce = salt + 8 bytes of the record -> the request
  THE RESULT, WITH THE LEAKED SERVER KEY:
    static RSA  opened
                POST /transfer?from=ACC-1001&to=ACC-2002&amount=2500
    DHE         not opened
    ECDHE       not opened
    unrelated   a key that is not the server's opened 0 of 3
