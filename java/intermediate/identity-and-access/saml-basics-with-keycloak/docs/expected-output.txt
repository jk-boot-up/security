== 1. Signing in through the bank ==
the shop sends the shopper to the bank with an authentication request: from http://127.0.0.1:<port>/saml2/service-provider-metadata/keycloak, to answer at http://127.0.0.1:<port>/login/saml2/sso/keycloak, unsigned, with an id of its own
ana signs in at the bank, never at the shop; the bank answers with a response signed as a whole and an assertion signed on its own: 2 signatures
the response answers the shop's request: true, is addressed to the shop's address: true, comes from the bank's realm: true
the assertion names ana: ana, is for the shop's entity id only: true, and lasts seconds: true
the shopper's browser posts it to the shop: signed in as ana
the shop's page for her: {"name":"ana","email":"ana@bank.example","registration":"keycloak","sessionIndexes":n}
== 2. A valid signature is not the same as the bank's signature ==
the bank's response with the name edited to admin   -> refused (invalid_signature)
admin, signed correctly with the attacker's own key -> refused (invalid_signature)  (2 signatures, every one of them valid XML)
a genuine response from the wallet, signed by the wallet -> refused (invalid_signature)  (answers the shop's request: true)
the shop trusts the key in the bank's metadata, and no other key, however valid the signature
== 3. A valid signature on one assertion, and another one read ==
response unsigned, an admin assertion first, the bank's signed one second -> refused (invalid_signature)
response unsigned, the bank's signed assertion first, an admin one second -> refused (invalid_signature)
no signature anywhere, admin -> refused (invalid_signature)
a response with a DOCTYPE that reads a file -> refused (malformed_response_data)
the shop reads the assertion that a trusted key signed, and only that one; a library does this and is kept patched
== 4. The statement itself is checked ==
genuine response, first time -> signed in as ana
the same response replayed from another browser -> refused (invalid_in_response_to)
the same response replayed from the same browser -> refused (invalid_in_response_to)  (the shop's request was used up)
a response posted 4 seconds after it was issued, to an assertion that lasts 2 -> refused (invalid_assertion)
a genuine response the bank signed for another shop -> refused (invalid_assertion)  (the signature is the bank's, the audience is not this shop)
a signature says who wrote the statement; the checks above say whether it is for this shop, this request, now
== 5. The bill: keys, metadata and XML ==
the shop reads the bank's metadata once, when it starts; a sign-in now -> signed in as ana
the bank adds a new signing key (201) and signs with it from now on; the next sign-in -> refused (invalid_signature)  <- EVERY SHOPPER IS REFUSED
the shop restarts and reads the metadata again; the next sign-in -> signed in as ana
so a bank that rotates its key needs the shop to reload its metadata first, and a plan for the hours between
XML signatures are hard to get right, which is why the shop uses OpenSAML through Spring Security, and why its patches matter
