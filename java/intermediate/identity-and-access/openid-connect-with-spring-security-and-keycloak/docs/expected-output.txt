ONE. OAuth gives access; OpenID Connect adds who signed in.
  THE REQUEST (the store sends Ana's browser to Keycloak):
    <keycloak>/realms/bank/protocol/openid-connect/auth
    response_type          code
    client_id              store-web
    scope                  openid email
    state                  <random, kept in her session>
    nonce                  <random, kept in her session>
    code_challenge         <SHA-256 of a random verifier>
    code_challenge_method  S256
  THE SIGN-IN:
    Ana types her password at Keycloak, not the store: true
    the store redeems the code, server to server: true
  THE ID TOKEN'S CLAIMS (19 claims, as the store sees them):
    iss    <keycloak>/realms/bank
    sub    a0a0a0a0-0000-4000-8000-000000000001
    aud    store-web, azp store-web, typ ID
    nonce  <random>, the one sent in this sign-in: true
    email  ana@mail.example, email_verified true
    also   acr, at_hash, auth_time, exp, family_name, given_name,
           iat, jti, name, preferred_username, sid
  THE RESULT:
    Ana is signed in to the store as
    <keycloak>/realms/bank | a0a0a0a0-0000-4000-8000-000000000001
  THE TWO TOKENS IN THE REPLY (Keycloak's token endpoint):
    ID token      typ ID      aud store-web: for the store
    access token  typ Bearer  no aud claim: for the API
  THE ACCESS TOKEN, OFFERED AS PROOF OF SIGN-IN:
    refused: invalid claims {aud=null}
    <- AN ACCESS TOKEN SAYS WHAT IS ALLOWED, NOT WHO
  A SIGN-IN WITHOUT THE openid SCOPE (scope email):
    no ID token in the reply: true; only API access
  A CALLBACK FROM ANOTHER SIGN-IN, IN ANA'S BROWSER:
    refused: no sign-in in this browser has that state
TWO. Checking the ID token, as OpenID Connect Core requires.
  THE STORE'S SETTINGS (every ID token is checked against them):
    issuer      https://bank.example
    client_id   store-web
    keys        the provider's jwks.json, key lab-key
    clock skew  30 seconds
  BEFORE SIGNING (a test provider makes the ID token):
    header  {"kid":"lab-key","alg":"RS256"}
    claims  aud, exp, iat, iss, sub; exp = iat + 300 s
  HOW IT IS SIGNED (step by step):
    1. header part = base64url(header)
       eyJraWQiOiJsYWIta2V5IiwiYWxnIjoiUlMyNTYifQ (42 chars)
    2. claims part = base64url(claims): 132 chars
    3. signing input = header part + "." + claims part
    4. signature = RSA(private key, SHA-256(signing input))
       a 2048-bit key gives 256 bytes = 342 base64url chars
  HOW SPRING SECURITY CHECKS IT (in this order):
    1. the signature, with the published key named by kid
    2. exp and iat against now, with 30 seconds of skew
    3. iss exactly, sub present, aud has store-web, azp
  THE RESULT:
    accepted
  ONE THING CHANGED AT A TIME (the input, then the result):
    signed with a key the bank never published, kid lab-key
      -> refused: Signed JWT rejected: Invalid signature
    iss https://bank.example/ (one extra slash)
      -> refused: invalid claims {iss=https://bank.example/}
    iss https://wallet.example, signed by the bank
      -> refused: invalid claims {iss=https://wallet.example}
    aud budget-app
      -> refused: invalid claims {aud=[budget-app]}
    aud [store-web, budget-app], no azp
      -> refused: invalid claims {azp=null}
    aud [store-web, budget-app], azp store-web
      -> accepted
  THE SUBJECT, THE HEADER AND THE NONCE (input, then result):
    no sub claim
      -> refused: invalid claims {sub=null}
    header {"alg":"none"}, no signature
      -> refused: Unsupported algorithm of none
    the nonce: checked by the sign-in itself, with the state,
      against the one kept in the browser's session (act one)
  THE TIME CHECK (skew 30 seconds):
    exp = now - 29 s: now < exp + 30
      -> accepted
    exp = now - 31 s: now > exp + 30
      -> refused: expired
