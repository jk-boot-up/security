ONE. OAuth gives access; OpenID Connect adds who signed in.
  the store sends Ana to the bank with scope "openid email", and a state, a nonce and a PKCE challenge kept for her browser: true
  Ana signs in at Keycloak, never at the store; the store redeems the code itself and starts her session: true
  the ID token's claims: [acr, at_hash, aud, auth_time, azp, email, email_verified, exp, family_name, given_name, iat, iss, jti, name, nonce, preferred_username, sid, sub, typ]
  Ana is signed in to the store as <keycloak>/realms/bank | a0a0a0a0-0000-4000-8000-000000000001, with the e-mail address ana@mail.example (verified: true)
  the nonce in her ID token is the one the store sent in this sign-in: true
  the reply holds two tokens: an ID token for the store (typ ID, audience store-web) and an access token for the bank's API (typ Bearer, audience claim: false)
  the access token handed to the store as proof of sign-in: refused (The ID Token contains invalid claims: {aud=null})  <- AN ACCESS TOKEN SAYS WHAT IS ALLOWED, NOT WHO SIGNED IN
  a sign-in that asks without the openid scope: no ID token in the reply: true, only API access
  a callback from another sign-in, carried to Ana's browser: refused (no sign-in started by this browser has that state)
TWO. Checking the ID token, as OpenID Connect Core requires.
  the bank's own ID token: accepted
  the same claims signed with a key the bank never published, under the bank's key id: refused (Signed JWT rejected: Invalid signature)
  issuer https://bank.example/ with one extra slash: refused (The ID Token contains invalid claims: {iss=https://bank.example/})
  issuer https://wallet.example, signed by the bank: refused (The ID Token contains invalid claims: {iss=https://wallet.example})
  audience budget-app: refused (The ID Token contains invalid claims: {aud=[budget-app]})
  audiences store-web and budget-app, with no azp: refused (The ID Token contains invalid claims: {azp=null}); with azp store-web: accepted
  29 seconds past its expiry, inside the 30 second skew: accepted; 31 seconds past: refused (expired)
  no subject: refused (The ID Token contains invalid claims: {sub=null})
  a header saying alg none: refused (Unsupported algorithm of none)
  the nonce is checked by the sign-in itself, against the one kept in the browser's session, and the state with it: see one
THREE. Discovery and keys.
  the store is configured with one value, the issuer <keycloak>/realms/bank
  it reads <keycloak>/realms/bank/.well-known/openid-configuration, which names the issuer it asked for: true
  the authorization, token and key addresses all start with the issuer's own address: true
  a document at that address naming the issuer https://wallet.example: refused (the metadata names another issuer)  <- ONE PROVIDER CANNOT POSE AS ANOTHER
  a document whose keys are on https://keys.example: accepted by Spring Security: true  <- IT CHECKS THE ISSUER, NOT WHERE THE KEYS ARE: THE ISSUER ADDRESS MUST BE https AND TRUSTED
  Keycloak publishes 1 signing key; a token signed with it: accepted
  the bank adds a second key and signs new tokens with it; it now publishes 2, and the new token names a key id the store has not seen: true
  the store reloads the key set on its own: a token signed with the old key: accepted; with the new key: accepted
  over real HTTP on this machine: metadata and keys loaded: true, an ID token from that provider accepted: true
FOUR. Who signed in: issuer and subject, never the email.
  the bank says a0a0a0a0-0000-4000-8000-000000000001 has the e-mail address ana@mail.example, verified: true
  the wallet says its user c0c0c0c0-0000-4000-8000-000000003301 also has the e-mail address ana@mail.example, verified: false
  a store that keys accounts by e-mail address: Mallory signs in with the wallet and gets: account of Ana  <- ACCOUNT TAKEOVER
  keyed by issuer and subject: Ana gets account of Ana, Mallory gets new account for wallet | c0c0c0c0-0000-4000-8000-000000003301
  userinfo with Ana's access token: 200, sub a0a0a0a0-0000-4000-8000-000000000001, the same subject as the ID token: true
  userinfo with the ID token instead: refused (401)
FIVE. Signing out, and the bill.
  Ana signs out at the store: the store's session ended: true
  her browser is sent to <keycloak>/realms/bank/protocol/openid-connect/logout with id_token_hint, post_logout_redirect_uri: true
  Keycloak ends its session and sends the browser back to the store: true
  signing in again asks for her password again: true
  Ana is signed in on a laptop and a phone: two Keycloak sessions: true
  Keycloak ends the laptop's session (204) and sends the store a back-channel logout token: the laptop signed in: false, the phone signed in: true
  a made-up logout token: refused (the store answered 400), the phone still signed in: true
  an ID token sent as a logout token: refused (the store answered 500), the phone still signed in: true
  OpenID Connect has many checks and options, so production code uses a certified library and a real provider
  the ID token is for the store only: never send it to an API, and never take an access token as a sign-in
  signing out must reach every party: the store, the provider, and through back-channel logout every other application
