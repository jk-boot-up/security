  THE REQUEST (the bank to ana's phone, through the browser):
    challenge  kppWym0d5TLqNpSHuZI4nNV6d9c1si0BD7r2Jf-Jes0
               32 random bytes, base64url
    rp id      bank.example
  THE CLIENT DATA (the browser writes it, not the page):
    {"type":"webauthn.create",
    "challenge":"kppWym0d5TLqNpSHuZI4nNV6d9c1si0BD7r2Jf-Jes0",
    "origin":"https://bank.example","crossOrigin":false}
  THE RESPONSE (a new P-256 key pair, made for bank.example):
    credential id  f8de8c471eaaf8bc92213f0e953b2e25 (16 bytes)
    public key     91 bytes, starts 3059301306072a86
    private key    stays on ana's phone
  THE BANK'S CHECKS (challenge, type, origin, rp id hash):
    accepted (passkey ana's phone registered)
  WHAT THE BANK STORES:
    credential id 16 bytes, public key 91 bytes, counter 0
    nothing that can sign
  A COPY OF THE RECORDS (another key, ana's credential id):
    refused (signature does not match)

THREE. A look-alike site gets nothing it can use.
  THE PAGE (a copy of the bank's page):
    https://bank-example.test
  REQUEST 1. A PASSKEY FOR ITS OWN NAME bank-example.test:
    nothing (the authenticator has no passkey for bank-example.test)
  REQUEST 2. THE BANK'S REAL CHALLENGE, RP ID bank.example:
    is bank-example.test equal to bank.example?  no
    does it end with .bank.example?  no
    nothing (bank.example is not this page's site)
  REQUEST 3. A BROWSER THAT SKIPPED THAT RULE:
    signed client data: "origin":"https://bank-example.test"
    the bank expects:   "origin":"https://bank.example"
    refused (wrong origin https://bank-example.test)
  THE SAME PAGE ASKS FOR ANA'S PASSWORD, AND SHE TYPES IT:
    replayed at the bank: accepted (signed in as ana with a password)
  a password can be phished; a passkey cannot
FOUR. User verification for payments, and counters against copies.
  A PAYMENT OF 900 (the bank asks for user verification):
    touch only, flags 01:
      refused (user verification required)
    touch and fingerprint, flags 05:
      accepted (signed in as ana with ana's phone)
  THE COUNTERS (the bank keeps the last one it saw):
    the bank has seen 6
    real phone:  counter 7, 7 > 6?  yes
      accepted (signed in as ana with ana's phone)
    copied key:  counter 7, 7 > 7?  no
      refused (counter 7 is not above 7: a cloned key?)
    real phone again, counter 8:
      refused (passkey suspended after a counter went backwards)
  A SYNCED PASSKEY (shared between ana's devices):
    counter 0: accepted (signed in as ana with ana's synced passkey)
    counter 0: accepted (signed in as ana with ana's synced passkey)
  a synced passkey always reports 0: a copy cannot be spotted
FIVE. The bill: recovery, lost devices and the move away from passwords.
  BEN'S WAYS IN:
    2 passkeys: his phone and a security key
    1 recovery code of 20 characters; the bank keeps its SHA-256
  BEN'S PHONE IS LOST:
    new laptop:
      nothing (the authenticator has no passkey for bank.example)
    security key:
      accepted (signed in as ben with ben's security key)
    recovery code, once:
      accepted (recovered ben; register a new passkey now)
    recovery code, twice:
      refused (recovery code unknown or already used)
  recovery is now the weakest way in: guard it like a passkey
  ANA'S OLD PASSWORD, STILL SWITCHED ON:
    accepted (signed in as ana with a password)  <- THE WEAKEST WAY IN
  ANA'S PASSWORD, SWITCHED OFF (she has two passkeys):
    refused (password sign-in is switched off for ana)
  a real bank uses a maintained WebAuthn library
