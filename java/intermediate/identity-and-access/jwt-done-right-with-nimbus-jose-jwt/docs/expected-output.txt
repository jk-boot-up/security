ONE. Three parts, and decoding is not verifying.
  the bank's authorization server issues ana an access token of 347 characters in 3 parts
  header: {"kid":"bank-2026-01","typ":"at+jwt","alg":"ES256"}
  claims: {"sub":"ana","aud":"accounts-api","nbf":1800000000,"scope":"accounts:read","iss":"https://auth.bank.example","exp":1800000300,"iat":1800000000}
  the third part is a 64-byte ES256 signature (R and S, 32 bytes each) over the first two
  anyone can read the claims: base64url is an encoding, not encryption, so no secret belongs in them
  the claims edited to sub=mallory, with ana's signature kept: a reader that only parses says mallory  <- PARSING IS NOT VERIFYING
  the validator: refused (Signed JWT rejected: Invalid signature)
TWO. The server chooses the algorithm, never the token.
  ana's token with the bank's key: accepted for ana
  the same claims with a header that says none and no signature: refused (Unsecured (plain) JWTs are rejected, extend class to handle)
  a header that says HS256, signed with the bank's public key as the shared secret: refused (Signed JWT rejected: Another algorithm expected, or no matching key(s) found)
  a correctly signed token of another type, offered as an access token: refused (JOSE header typ (type) id+jwt not allowed)
  the algorithm and the type are settings of the API; the header is only checked against them
THREE. Every claim that matters is checked.
  at the moment of issue: accepted for ana
  20 seconds after exp, inside the 30 seconds allowed for clock skew: accepted for ana
  31 seconds after exp: refused (Expired JWT)
  a token that starts in 2 minutes, presented now: refused (JWT before use time)
  issued by another authorization server: refused (JWT iss claim value rejected)
  meant for the loyalty API, sent to the accounts API: refused (JWT aud claim rejected)
  with only the scope cards:read: refused (missing scope accounts:read)
  a valid signature proves who wrote the token; only the claims say whether it is for this API, now
FOUR. Keys by id, from the one set the API was configured with.
  the bank publishes 1 key, bank-2026-01; the first token: accepted for ana
  100 more tokens: the key set endpoint was asked 1 time in all, the rest came from the cache
  a token naming a key id the API has never seen: refused (Signed JWT rejected: Another algorithm expected, or no matching key(s) found); the key set endpoint has now been asked 2 times
  100 more of them: the key set endpoint was asked 0 more times (a minimum time between refetches protects it)
  a token signed with another key but naming the bank's key id: refused (Signed JWT rejected: Invalid signature)
  a token whose header points at the attacker's own key set (jku): refused (the key set could not be asked again so soon (RateLimitReachedException)); the attacker's server was asked 0 times
  a token that carries its own public key in the header (jwk): refused (the key set could not be asked again so soon (RateLimitReachedException))
  the bank publishes bank-2026-07 before using it; after the cache time the API trusts 2 keys: the old token accepted for ana; asked 3 times
  the bank signs with the new key: accepted for ana
  the old key is retired and no longer published; inside the cache time the old token: accepted for ana  <- A RETIRED KEY LIVES ON IN THE CACHE
  after the cache time the old token: refused (Signed JWT rejected: Another algorithm expected, or no matching key(s) found); asked 5 times (the cache expired, and the unknown key id made the library ask once more before giving up)
  keys come from the URL in the API's settings and from nowhere a token names: every one of the 5 fetches was for that URL
FIVE. The bill: a token cannot be taken back.
  ana's access is removed 2 minutes after her token was issued
  2 minutes later her access token: accepted for ana  <- STILL WORKS UNTIL IT EXPIRES
  her refresh token, which the server looks up: refused (revoked)
  at 5 minutes and 31 seconds the access token: refused (Expired JWT)
  so access tokens live for minutes, and a token asking for more than 15 is refused: refused (lifetime longer than the policy allows)
  where a browser should keep tokens is the tokens-in-the-browser project; the library does the parsing, the signature and the claims, and the policy stays ours
