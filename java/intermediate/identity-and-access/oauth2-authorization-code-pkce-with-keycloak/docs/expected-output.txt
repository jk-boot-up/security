ONE. The authorization code flow, step by step.
  STEP 1, THE REQUEST (the app sends Ana's browser to Keycloak):
    GET <keycloak>/realms/bank/protocol/openid-connect/auth
      ?response_type=code
      &client_id=budget-app
      &redirect_uri=https://budget.example/callback
      &scope=openid accounts.read
      &state=<state>
      &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
      &code_challenge_method=S256
  STEP 2, AT KEYCLOAK (never at the app):
    Ana signs in with her bank password
    the consent page asks for "Read your accounts": true
    Ana agrees
  STEP 3, THE RESPONSE (Keycloak sends the browser back):
    302 Location: https://budget.example/callback
      ?state=<state>
      &session_state=<session>
      &iss=<keycloak>/realms/bank
      &code=<code>
    the state comes back unchanged: true
    iss names the bank realm: true
  STEP 4, THE REQUEST (the app calls Keycloak directly):
    POST <keycloak>/realms/bank/protocol/openid-connect/token
      grant_type=authorization_code
      client_id=budget-app
      code=<code>
      redirect_uri=https://budget.example/callback
      code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
  STEP 5, THE RESPONSE (to the app, not to the browser):
    access_token=<access token>  lives 300 s (exp - iat)
    refresh_token=<refresh token>
    id_token=<id token>
    scope=openid accounts.read
  INSIDE THE ACCESS TOKEN (a JWT signed by Keycloak):
    aud=accounts-api  azp=budget-app
    iss=<keycloak>/realms/bank
    sub=a0a0a0a0-0000-4000-8000-000000000001 (Ana)
    scope=openid accounts.read
    no password, no e-mail address: true
  STEP 6, THE APP CALLS THE BANK'S API:
    GET /accounts  Authorization: Bearer <access token>
    -> 200 ana: 2 accounts
    GET /accounts with no token
    -> 401
  WHO SAW WHAT:
    the app never saw Ana's password
    the browser never saw the access token
TWO. PKCE: a code is useless without the verifier.
  THE VERIFIER (made by the app for one sign-in, kept secret):
    dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
    43 characters from A-Z a-z 0-9 - . _ ~ (the RFC 7636 example)
  HOW THE S256 CHALLENGE IS MADE:
    1. the 43 characters as 43 ASCII bytes:
       64 42 6a 66 74 4a 65 5a 34 43 56 50 2d 6d 42 39 ...
    2. SHA-256 of those bytes, always 32 bytes:
       13 d3 1e 96 1a 1a d8 ec 2f 16 b1 0c 4c 98 2e 08
       76 a8 78 ad 6d f1 44 56 6e e1 89 4a cb 70 f9 c3
    3. base64url: every 3 bytes become 4 characters of 6 bits
       13 d3 1e = 000100 111101 001100 011110 = 4 61 12 30 = E9Me
    4. 32 bytes become 43 characters, with no = padding:
       E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
    the same as the challenge RFC 7636 publishes: true
    the same as OAuthClient.challenge, with Java's Base64: true
  WHAT TRAVELS THROUGH THE BROWSER (step 1):
    the challenge: true
    the verifier: false
  THE LEAK (a thief redeems a copied code before the app):
    the thief, with no verifier
      -> refused: invalid_grant
         PKCE code verifier not specified
    then the budgeting app, with the real verifier
      -> refused: invalid_grant
         Code not valid
  a failed try burns the code: the leak is useless, Ana signs in again
  A NEW CODE, AND A VERIFIER THE THIEF MADE UP (43 x's):
    -> refused: invalid_grant
       PKCE verification failed: Code mismatch
  A NEW CODE, AND THE REAL VERIFIER:
    -> tokens issued
  WEAKER REQUESTS, REFUSED BY KEYCLOAK:
    code_challenge_method=plain (the verifier itself travels)
      -> refused: invalid_request
         Invalid parameter: code challenge method is not matching the
         configured one
    no code_challenge at all
      -> refused: invalid_request
         Missing parameter: code_challenge_method
THREE. Exact redirect addresses, state, and codes that work once.
  THE REGISTERED ADDRESS (Keycloak compares it exactly):
    https://budget.example/callback
  THE ADDRESS IN THE REQUEST:                  EXACT    PREFIX
    https://budget.example/callback            code     code
    https://budget.example/callback/../steal   refused  code
    https://budget.example.evil.test/callback  refused  code
    https://budget.example/callback?next=evil  refused  code
    https://BUDGET.example/callback            refused  refused
    https://budget.example/callback/           refused  code
  each refusal is a page at Keycloak, with no redirect:
    Invalid parameter: redirect_uri
  a prefix check on https://budget.example sends the code away 4 times
  THE ATTACK (login forgery):
    Ana's browser opens a callback link with the attacker's code
    and state, to sign Ana in to the attacker's account
  THE APP'S CHECK (the state against Ana's browser session):
    -> refused: invalid_state
       this browser did not start this sign-in
  ONE CODE, REDEEMED TWICE:
    first: tokens issued, GET /accounts -> 200
    second, by whoever copied the code:
      -> refused: invalid_grant
         Code not valid
    the first access token now:
      at Keycloak (userinfo) -> 401  <- THE SESSION IS ENDED
      at the API (own signature check) -> 200  <- UNTIL IT EXPIRES
  ONE CODE, REDEEMED 11 SECONDS LATER (this realm gives codes 10):
    by the budgeting app, with the real verifier
      -> refused: invalid_grant
         Code not valid
FOUR. Scopes and refresh tokens.
  THE SCOPE (asked for, agreed to, carried by the token):
    openid accounts.read
  THE API CALLS WITH THAT TOKEN:
    GET /accounts -> 200
    POST /payments -> 403 insufficient_scope
  ASKING FOR payments.write TOO (never registered):
    -> refused: invalid_scope
       Invalid scopes: openid accounts.read payments.write
  THE REFRESH (access token A1 ran out; the app sends R1):
    R1 -> a new access token A2 and a new refresh token R2
    R2 differs from R1, and A2 from A1: true
  THE THEFT (a thief copied R1 and replays it):
    R1 again
      -> refused: invalid_grant
         Maximum allowed refresh token reuse exceeded
    R2, held by the real app
      -> refused: invalid_grant
         Session doesn't have required client
    A2 at Keycloak (userinfo) -> 401  <- THE SESSION IS ENDED
  AN ACCESS TOKEN 331 SECONDS OLD (300, plus 30 for clock skew):
    GET /accounts -> 401
FIVE. Current practice, and the bill.
  THE IMPLICIT FLOW (response_type=token: a token in the address):
    -> refused: unauthorized_client
       Client is not allowed to initiate browser login with given
       response_type. Implicit flow is disabled for the client.
  THE PASSWORD GRANT (the app would hold Ana's password):
    -> refused: unauthorized_client
       Client not allowed for direct access grants
  both are removed by RFC 9700 and by OAuth 2.1
  A CONFIDENTIAL CLIENT (statements-service, on a server):
    a wrong client secret
      -> refused: unauthorized_client
         Invalid client or Invalid client credentials
    the right secret, but a code it was never given
      -> refused: invalid_grant
         Code not valid
    the right secret and a real code, but no verifier
      -> refused: invalid_grant
         PKCE code verifier not specified
  a secret does not replace PKCE; a phone app has no secret at all
  WHAT THE API CHECKS ON EVERY TOKEN (it keeps no session):
    Keycloak's signing key, the issuer, the audience accounts-api,
    the dates and the scope
  in production: TLS, backups, key rotation, login monitoring
