ONE. What a security log must answer.
  the bank's old logger wrote 8 lines this morning, for example:
    2026-10-18T09:01:00Z ERROR login failed
    2026-10-18T09:05:00Z INFO transfer done amount=500
  the question: who moved 500 from ANA-1 to MAL-9, and from where?
  old lines that mention ANA-1: 0  <- THE LOG CANNOT ANSWER
  the security log records who, what, when, where from, the outcome and a request id for each of 8 events
  the transfer: by ana, from 198.51.100.66, at 2026-10-18T09:05:00Z, success, request req-0006
  the same address before it: 2 failed logins as ana, then 1 success  <- SOMEONE WITH ANA'S PASSWORD, NOT ANA
  event types in the log: [login, access-decision, money-movement, admin-change]
TWO. What never to log.
  the old logger's card payment line holds the full card number: true  <- A BREACH OF THE LOG IS A BREACH OF THE CARDS
  the password tried in a failed login: [removed]
  the session id of the new login: [removed]
  the transfer's Authorization header: [removed]
  the card payment: card ************1111, and a card number typed into the note: "paid with ************1111"
  secrets from the morning's events found anywhere in the security log: 0 of 5
  secrets are removed by field name, and card numbers and tokens also by their shape, so free text is covered too
THREE. Text that tries to write the log.
  a username typed into the login form: "mallory\n2026-10-18T09:09:00Z INFO login ok user=admin"
  the old logger's file now has 2 lines; the second reads: 2026-10-18T09:09:00Z INFO login ok user=admin  <- A FORGED LINE
  the security log wrote 1 line; read back, the actor is exactly what was typed: true, and the outcome is failure
  a username carrying a quote and a fake field: the outcome still reads failure, and the actor is the text as typed: true
  structured output escapes text instead of trusting it, and keeps it whole, so investigators see exactly what was sent
FOUR. A log that shows it was changed.
  each line carries the SHA-256 of the line before it; the morning's 8 lines: intact
  line 6, the transfer, deleted: broken at line 6
  line 6's amount edited from 500 to 50: broken at line 7
  the last line edited: intact  <- NOTHING FOLLOWS THE LAST LINE TO GIVE IT AWAY
  compared with the latest hash, published somewhere else as each line is written: does not match, so the change is found
  the file is written by appending only, with permissions rw-------
  an attacker with root can still rewrite the whole file and its chain, which is why the log must also leave the host
FIVE. The bill.
  every line is also shipped to a second store as it is written; the attacker deletes the local log: local 0 lines, shipped 8 lines, intact
  names and addresses make the log personal data, so it is kept for a fixed time: keeping 30 days, on day 41 10 old lines go and 30 stay
  the kept lines check from the anchor written down when the old ones went: intact
  the morning's lines average 291 bytes, so 2000000 logins a day write about 582 megabytes a day for logins alone: volume needs a budget
  and a log that nobody reads is evidence only after the fact: the -with-loki-and-grafana version ships, queries and alerts
