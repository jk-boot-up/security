ONE. The attack.
  THE ATTACKER'S SCRIPT (the same in all three runs):
    01:00  gets into web01 through a flaw in the application
    01:05  reads the database password from the configuration
    01:20  starts copying the customer table from db01
    01:40  adds three ways back in: cron job, SSH key, svc-backup
  HOW FAST THE DATA GOES:
    rate      1000 rows a minute, from 01:20
    table     50000 customers
    all gone  50000 / 1000 = 50 minutes later, at 02:10
  THE WAYS BACK IN, AND WHAT CLOSES EACH:
    cron job on web01                  rebuild from the image
    SSH key on web01                   rebuild from the image
    hidden admin account svc-backup    find in logs, then disable
    unpatched flaw in the application  patch the flaw
    stolen database password           rotate the password
TWO. What was prepared.
  THE SIX THINGS, DECIDED BEFORE THE ATTACK:
                                     nothing   alert    full
    runbook and contact list              no      no     yes
    alert on unusual database reads       no     yes     yes
    logs kept centrally 7+ days           no      no     yes
    snapshot of memory and disk           no      no     yes
    known-good image to rebuild           no      no     yes
    tested backups                        no      no     yes
    in place                          0 of 6  1 of 6  6 of 6
  WHEN THE BREACH IS FOUND:
    nothing     by a customer  3 x 24 x 60 = 4320 min, day 3 01:00
    alert only  by the alert   30 min, day 0 01:30
    full        by the alert   30 min, day 0 01:30
THREE. Response A: nothing prepared, and a panicked fix.
  BEFORE THE RESPONSE (day 3 01:00):
    rows copied   50000 of 50000, all gone since day 0 02:10
    ways back in  5 of 5 open
  THE RESPONSE (day 3):
    01:00  detect              a customer says their data is sold
    01:03  reboot web01        memory lost; cron job, SSH key stay
    01:13  rotate db password  the stolen password stops working
    01:23  reconnect web01     back in service, 4 ways in open
    03:23  monitor 2 hours     THE ATTACKER IS BACK
  AFTER THE RESPONSE:
    copying stopped  never: all 50000 rows were gone
    ways back in     4 of 5 open
      cron job on web01
      SSH key on web01
      hidden admin account svc-backup
      unpatched flaw in the application
    evidence         memory no, disk no, logs no
    root cause       unknown: no central logs
    out of service   01:03 to 01:23 = 20 min
    the attacker     came back: cron job on web01
FOUR. Response B: an alert, but no plan.

  THE RESPONSE (day 0):
    01:30  detect              alert: unusual database reads
    01:35  isolate web01       memory kept, route to db01 cut
    03:35  rebuild web01       by hand, no image: is it clean?
    03:45  reconnect web01     back in service, 3 ways in open
    05:45  monitor 2 hours     THE ATTACKER IS BACK
  AFTER THE RESPONSE:
    copying stopped  (01:35 - 01:20) x 1000 = 15000 rows
    ways back in     3 of 5 open

      unpatched flaw in the application
      stolen database password
    evidence         memory no, disk no, logs no
    root cause       unknown: no central logs

FIVE. Response C: the playbook.
  BEFORE THE RESPONSE (day 0 01:30):
    rows copied   (01:30 - 01:20) x 1000 = 10000 of 50000
    ways back in  5 of 5 open
  THE RESPONSE (day 0):
    01:30  detect              alert: unusual database reads
    01:35  isolate web01       memory kept, route to db01 cut
    01:37  kill db sessions    attacker's db01 session ended
    01:52  capture evidence    memory, disk and logs, with hashes
    02:12  scope from logs     start 01:00; svc-backup made 01:40
    02:22  rotate db password  the stolen password stops working
    02:25  disable svc-backup  hidden admin account removed
    02:55  patch the flaw      the way in is closed
    03:35  rebuild web01       from the image: cron job, key gone
    03:45  reconnect web01     back in service, 0 ways in open
    05:45  monitor 2 hours     quiet: nobody came back
  AFTER THE RESPONSE:
    copying stopped  (01:35 - 01:20) x 1000 = 15000 rows
    ways back in     0 of 5 open
    evidence         memory yes, disk yes, logs yes
    root cause       known: 30 days of central logs reach 01:00
    out of service   01:35 to 03:45 = 130 min
    the attacker     did not come back
