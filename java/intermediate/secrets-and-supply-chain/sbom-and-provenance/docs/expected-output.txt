ONE. What a bill of materials answers, and what it does not.
  the release shop-1.4.0.jar is built from 3 files and depends on 3 libraries
  the CycloneDX 1.6 SBOM lists, each with a SHA-256: pkg:maven/com.acme/acme-http@3.0.2, pkg:maven/com.acme/acme-json@2.4.1, pkg:maven/com.acme/acme-log@1.9.0
  this SBOM is the one for this jar: true
  a library jar changed after the SBOM was written is found: [pkg:maven/com.acme/acme-json@2.4.1]
  which repository, branch and commit the jar was built from: the SBOM does not say
  who built it, and on which machine: the SBOM does not say  <- THAT IS WHAT PROVENANCE IS FOR
TWO. Provenance: who built it, from what.
  an in-toto statement, predicate https://slsa.dev/provenance/v1
  subject: shop-1.4.0.jar, sha256 38a6dd0dd912fc89...
  build type: https://build.shop.example/gradle-jar/v1
  source: https://git.shop.example/shop/store, refs/heads/main, commit 4f1c2a9e8b7d...
  builder: https://build.shop.example/runner/v1
  signed in a DSSE envelope over the encoding: DSSEv1 28 application/vnd.in-toto+json 768 {...}
  the Ed25519 signature verifies with the builder's key shop-ci-2026: true
  the same signed bytes offered as another payload type: refused (the payload is not an in-toto statement)
THREE. Checking before deploying.
  the release from the trusted builder, built from main: deployed
  a build of a fork: refused (built from another repository)
  a build of an unreviewed branch: refused (built from another branch)
  a build signed on a developer's laptop: refused (no signature from a trusted builder)
  the trusted key, but a statement naming the staging runner: refused (built by a builder that is not trusted)
  the fork's statement edited after signing to say main's repository: refused (the signature does not match the statement)
  the fork's jar offered with the real release's provenance: refused (the statement is about another artifact)
  a jar with no provenance at all: refused (no provenance)
FOUR. SLSA build levels, and builds that can be repeated.
  a developer's laptop build: level 0, held back because it writes no provenance
  a laptop build that signs its own provenance: level 1, held back because the provenance is signed with a key the developer holds, so the developer could forge it
  the store's hosted CI runner: level 2, held back because build steps run where the signing key can be reached, so a malicious build could sign anything
  a hardened build platform with isolated, short-lived builds: level 3
  two careless builds of the same commit (own clock, file-system order) give the same jar: false
  two reproducible builds (commit time, sorted entries) give the same jar: true, sha256 38a6dd0dd912fc89...
  so anyone can rebuild the commit and check it against the provenance subject: true
FIVE. The bill.
  a deploy script that never checks runs the fork's build: deployed  <- PROVENANCE ONLY HELPS WHEN IT IS CHECKED
  with the builder's key stolen, a fork's jar with a statement claiming main: deployed  <- PROTECT THE KEY AND THE BUILDER
  the SBOM written for 1.4.0, checked against the 1.4.1 jar: describes it false  <- WRITE THE SBOM AT EVERY BUILD
  and a correct SBOM is only useful if something scans it against new advisories: see the -with-syft-and-grype version
