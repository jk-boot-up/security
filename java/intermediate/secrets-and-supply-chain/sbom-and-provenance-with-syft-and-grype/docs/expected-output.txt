ONE. What a bill of materials answers, and what it does not.
  syft catalogues the image shop-sbom:2.14.1 and writes a CycloneDX JSON bill of materials: true, with operating system packages: true and libraries: true
  the application's libraries, each by its package URL: [pkg:maven/org.apache.logging.log4j/log4j-api@2.14.1, pkg:maven/org.apache.logging.log4j/log4j-core@2.14.1]
  each library jar carries its SHA-1: true, and its licence: true
  the bill of materials names the image, and not the repository, the commit or the builder: true  <- THAT IS WHAT PROVENANCE IS FOR
TWO. Scanning it against known advisories.
  grype reads the image and matches its packages to its vulnerability database: critical advisories in log4j: [CVE-2021-44228, CVE-2021-45046], high: [CVE-2021-45105]
  each says which version fixes it: [2.15.0, 2.16.0, 2.17.0]
  scanning the bill of materials alone, not the image, finds the same advisories in log4j: true
  the rest of the findings come from the base image's operating system packages: true  (their number changes every day, so it is not printed)
  the image was never run: the bill of materials is read from its layers
THREE. Fixing it, and checking that it is fixed.
  the upgrade that clears every critical and high advisory in log4j is 2.17.0 or later; the team builds shop-sbom:2.25.5
  the new bill of materials differs in exactly the libraries that changed: removed [pkg:maven/org.apache.logging.log4j/log4j-api@2.14.1, pkg:maven/org.apache.logging.log4j/log4j-core@2.14.1], added [pkg:maven/org.apache.logging.log4j/log4j-api@2.25.5, pkg:maven/org.apache.logging.log4j/log4j-core@2.25.5]
  the base image's packages are the same in both: true
  the scan of the new image: critical and high advisories in log4j: 0, where the old image had 3
FOUR. A gate that reads the scan.
  the gate refuses a critical or high advisory in the store's own libraries; shop-sbom:2.14.1: refused (2 critical and 1 high advisories)
  an exception for a high advisory cannot cover a critical one: the same image with the exception written down: refused (2 critical and 0 high advisories)
  shop-sbom:2.16.0, which fixes the critical ones: refused (0 critical and 1 high advisories)
  with the written exception, on day 100: deployed with exceptions for its high advisories; on day 130, after it ran out on day 120: refused (0 critical and 1 high advisories)
  shop-sbom:2.25.5: deployed
  an exception names the advisory, the reason and the day it ends, so that it is reviewed and cannot stay for ever
FIVE. The bill.
  the same log4j-core 2.14.1 jar, renamed blob.dat inside another image: the bill of materials lists a log4j library: false, the scan finds a log4j advisory: false  <- A SCANNER FINDS ONLY WHAT THE CATALOGUER RECOGNISES
  the bill of materials written for shop-sbom:2.14.1, offered for shop-sbom:2.25.5: describes it false  <- WRITE THE BILL AT EVERY BUILD
  the database that the scan matches against is data: it was built 7 days ago or less
  an advisory published tomorrow will match a bill of materials written today, so the bills must be kept and scanned again on a schedule
  a finding is a question, not a verdict: a vulnerable library the store never calls is still reported; a statement of exploitability (VEX) records the answer
  the signed provenance of how the image was built, which this bill does not hold, is in the plain sbom-and-provenance project and in the cosign project
