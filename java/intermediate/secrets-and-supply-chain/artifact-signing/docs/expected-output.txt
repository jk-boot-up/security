ONE. A deployment that runs whatever arrives.
  BEFORE THE MIRROR (what the release team built):
    file      shop-app-2.4.0.jar, 2440 bytes
    byte 700  '/' (0x2f)
    sha256    4577e6b10a2f145d...
  AFTER THE MIRROR (what the deployment downloaded):
    file      shop-app-2.4.0.jar, 2440 bytes
    byte 700  '.' (0x2e)  <- ONE BIT FLIPPED
    sha256    6d6cca4f654956e0...  <- A NEW DIGEST
  THE TRUSTING DEPLOYMENT STEP:
    accepted  deployed shop-app-2.4.0.jar without checking it
    <- AN ALTERED JAR IS RUNNING
  WHY A DIGEST NEXT TO THE FILE DOES NOT HELP:
    whoever can change the file can change the digest beside it
TWO. A signed release, checked before it runs.
  BEFORE SIGNING (the statement, 151 bytes of text):
    release-statement/v1
    name=shop-app
    version=2.4.0
    channel=stable
    sha256=4577e6b10a2f145d... (64 hex digits)
    signed-day=120
  AFTER SIGNING (Ed25519 with the key stable-2026a):
    public key  797d4b479b52e839... (32 bytes)
    signature   6caf4ae3bad1f0aa... (64 bytes)
    again       the same signature: Ed25519 is deterministic
  HOW THE DEPLOYMENT CHECKS (it pins stable-2026a):
    1 parse    the statement is in its one exact form
    2 key      the key id is one the deployment pinned
    3 verify   Ed25519(public key, statement, signature)
    4 channel  the key and the statement are for stable
    5 dates    signed while the key was trusted
    6 digest   sha256(jar) equals the signed sha256
  THE RESULTS:
    the real jar      accepted  signed by stable-2026a
    one byte changed  refused   jar differs from the signed digest
    edited to 2.4.1   refused   bad signature
    a forged key      refused   bad signature
    an unknown key    refused   unknown key attacker-1
    no signature      refused   no signature
THREE. Signing keys: per channel, rotated, revoked.
  A BETA BUILD, OFFERED TO THE STABLE DEPLOYMENT:
    beta-2026a  refused   beta-2026a signs beta, not stable
  THE ROTATION (the stable keys, by day):
    stable-2026a  trusted from day 0, revoked on day 130
    stable-2026b  added on day 100
    the overlap   130 - 100 = 30 days, day 100 to 129
  SIGNED ON A DAY, THE VERDICT:
    day 110  stable-2026a  accepted  signed by stable-2026a
    day 110  stable-2026b  accepted  signed by stable-2026b
    day 120  stable-2026a  accepted  signed by stable-2026a
    day 140  stable-2026a  refused   signed day 140, revoked day 130
  BEFORE: A THIEF WITH stable-2026a, ON DAY 150:
    jar       a different one, sha256 14669a56d76a94fc...
    writes    signed-day=120, before the revocation
  AFTER: THE VERDICT:
    accepted  signed by stable-2026a
    <- A BACKDATED SIGNATURE: THE SIGNER WRITES THE DAY

  THE SIGNED HEAD:

  THE PROOF THAT ENTRY 1 IS IN THE LOG (1 hash):
    proof     leaf 0 = 05e76fd5f6c4ca1a

    checks    equals the signed root: true

FIVE. The bill.
  THE GATE GUARDS ONE PATH:
    an unsigned jar   refused   no signature
    copied by hand    never meets the gate: lock the other paths
  THE SIGNING KEY IS THE CROWN JEWEL:
    here         made from a fixed demo seed
    in practice  in a hardware module; each use approved
  ROTATION IS A PROJECT:
    every deployment trusts the new key before the old one
    is revoked: here an overlap of 30 days
  KEYLESS SIGNING (the -with-cosign version):
    short-lived certificates tied to an identity, in a public log
