ONE. A deployment that runs whatever arrives.
  the release team builds shop-app-2.4.0.jar: 2440 bytes, sha256 4577e6b10a2f145d
  the deployment downloads it from a mirror where one byte was changed: sha256 6d6cca4f654956e0
  the trusting deployment step: accepted (deployed shop-app-2.4.0.jar without checking it)  <- AN ALTERED JAR IS RUNNING
  a digest published next to the file does not help: whoever can change the file can change the digest beside it
TWO. A signed release, checked before it runs.
  the statement: name=shop-app version=2.4.0 channel=stable sha256=4577e6b10a2f145d... signed-day=120
  signed with stable-2026a: an Ed25519 signature of 64 bytes, the same on every run: 6caf4ae3bad1f0aa...
  the deployment pins the public key of stable-2026a and checks before it deploys
  the real jar: accepted (signed by stable-2026a for shop-app 2.4.0)
  the jar with one byte changed: refused (the artifact does not match the signed digest)
  the statement edited to version 2.4.1, signature kept: refused (the signature does not match)
  signed by another key that calls itself stable-2026a: refused (the signature does not match)
  signed by a key the deployment does not know: refused (unknown key attacker-1)
  no signature at all: refused (no signature)
THREE. Signing keys: one per channel, rotated with an overlap, revoked.
  a beta build signed with beta-2026a, offered to the stable deployment: refused (key beta-2026a signs for beta, not stable)
  day 100: stable-2026b is added, and both stable keys are trusted while the build moves over
  signed on day 110 with stable-2026a: accepted (signed by stable-2026a for shop-app 2.4.0)
  signed on day 110 with stable-2026b: accepted (signed by stable-2026b for shop-app 2.4.0)
  day 130: stable-2026a is revoked
  a release it signed on day 120, before the revocation: accepted (signed by stable-2026a for shop-app 2.4.0)
  a release it signed on day 140: refused (signed on day 140, after key stable-2026a was revoked on day 130)
  but the signer writes the day: a thief with the old key signs a different jar on day 150 and dates it day 120: accepted (signed by stable-2026a for shop-app 2.4.0)  <- A BACKDATED SIGNATURE
FOUR. A public log that every signature must be in.
  the store logs its releases: 2.3.0 on day 90 and 2.4.0 on day 120; the log's head: size 2, root c1e815c249fdd097..., signed by the log: true
  the proof that 2.4.0 is in the log: 1 hash, and it checks against the signed head: true
  the deployment, now requiring a log entry: accepted (signed by stable-2026a for shop-app 2.4.0, logged as entry 1)
  the thief's backdated jar, not logged: refused (the signature is not in the public log)
  the thief's backdated jar, logged on day 150: refused (logged on day 150, after key stable-2026a was revoked on day 130)  <- THE LOG'S DAY, NOT THE SIGNER'S
  the store's monitor reads the log and reports: entry 2: version 2.4.0 signed with stable-2026a, digest 14669a56d76a94fc is not a release the store made
  a log operator who hides the entry from the monitor shows two views, both signed by the log, both of size 3: roots f230f49e340792fc... and 92f28850530761dd...
  each view still extends the earlier head of size 2: true and true
  but two signed heads of the same size with different roots cannot both be true: the monitor and the customer compare heads, and the fork is proved: true
FIVE. The bill.
  the gate refuses an unsigned jar: refused (no signature)
  but it protects only the paths that pass through it: a jar copied straight onto a server never meets the gate
  the signing key is the crown jewel: here it comes from a fixed demo seed; in practice it stays in a hardware module, and each signing is approved and logged
  rotation is a project: every deployment must trust the new key before the old one is revoked, here an overlap of 30 days
  keyless signing replaces long-lived keys with short-lived certificates tied to an identity and recorded in a public log: the -with-cosign version
