ONE. A secrets server, and who may ask.
  THE POLICY FOR shop-api (reports has the same, with its name):
    path "secret/data/shop-api/*" { capabilities = ["read"] }
    path "database/creds/shop-api" { capabilities = ["read"] }
  THE REQUEST: POST auth/approle/login
    role_id    shop-api's role id (not shown)
    secret_id  a fresh one that works once (not shown)
  THE RESPONSE:
    status     allowed (200)
    token      policies [default, shop-api], 120 seconds
  THE SAME SECRET ID AGAIN, AS A THIEF WHO SAW IT WOULD:
    status     refused (400)
  A SECRET ID NOBODY ISSUED:
    status     refused (400)
  HOW THE POLICY DECIDES A READ:
    token     path                           rule     OpenBao
    shop-api  secret/data/shop-api/payment   allowed  allowed (200)
    shop-api  secret/data/reports/warehouse  refused  refused (403)
    shop-api  database/creds/reports         refused  refused (403)
    reports   secret/data/reports/warehouse  allowed  allowed (200)
    reports   secret/data/shop-api/payment   refused  refused (403)
    none      secret/data/shop-api/payment   refused  refused (403)
TWO. Secrets that stay still: versions, rotation and the audit trail.
  BEFORE THE ROTATION, WHAT THE STORE READS:
    current    {api-key=key-v1}
  AFTER THE PROVIDER ISSUES v2 (written as version 2):
    version 1  {api-key=key-v1}
    version 2  {api-key=key-v2}
    current    {api-key=key-v2}
  DESTROYING VERSION 1, ONCE EVERY SERVER HAS SWITCHED:
    by the application  refused (403)
    by the operator     allowed (204)
    then version 1      refused (404)
    then version 2      allowed (200)
  THE AUDIT TRAIL:
    requests for secret/data/shop-api/payment  true
    the application that asked, shop-api       true
    the key itself, key-v1 or key-v2           false
  HOW THE AUDIT TRAIL HIDES A VALUE (HMAC-SHA256, server's key):
    key-v2 becomes  hmac-sha256: + 64 hex characters (not shown)
    that exact hash is in the audit trail: true
THREE. Database logins that are leased.
  THE ROLE shop-api (what OpenBao runs to make each login):
    CREATE ROLE "{{name}}" WITH LOGIN PASSWORD '{{password}}'
      VALID UNTIL '{{expiration}}';
    GRANT SELECT ON orders TO "{{name}}";
    time to live 8 s, maximum 20 s
  THE REQUESTS: GET database/creds/shop-api, .../reports
  THE RESPONSES (names end in random letters, not shown):
    shop-api  v-approle-shop-api-...: true, lease 8 s
    reports   v-approle-reports-...: true, a different login: true
  WHAT THE LOGINS CAN DO IN THE REAL DATABASE:
    both connect                 true, true
    shop-api reads orders        true
    shop-api reads card_numbers  false
  THE SHOP RENEWS AND ASKS FOR 600 SECONDS:
    status   allowed (200)
    granted  min(600, 20 - its age) s, so at most 20: true
  AFTER 9.5 SECONDS (past the 8 s time to live):
    reports, never renewed, connects  false
    shop-api, renewed, connects       true
  THE OPERATOR REVOKES THE SHOP'S LEASE:
    status   allowed (204), the login connects: false
FOUR. Rotation, and the blast radius of a leak.
  BEFORE THE ROTATION (the static login payments):
    a thief copies its password, which connects: true
  AFTER THE ROTATION (POST database/rotate-role/payments):
    the new password differs   true
    the new password connects  true
    the thief's copy connects  false
  BEFORE THE REVOCATION (3 leased logins of shop-api):
    all connect, and a thief copies one: true
  AFTER REVOKING EVERY LEASE UNDER database/creds/shop-api:
    status                     allowed (204)
    logins that still connect  0 of 3
    reports still gets one     allowed (200)
FIVE. The bill.
  THE OPERATOR SEALS OpenBao, AS IN AN INCIDENT:
    status                  allowed (204)
  WHILE IT IS SEALED:
    the payment key         refused (503)
    a new login             refused (503)  <- NO NEW SERVER STARTS
    a login it already has  connects: true
  AFTER UNSEALING WITH THE KEY:
    status                  allowed (200)
    the payment key         allowed (200)
  WHAT IT COSTS:
    OpenBao holds every secret: guard, audit and back it up
    this dev server keeps all in memory; a real one stores it
    the first credential, role id and secret id, remains
    applications must take a new login without a restart
