ONE. Choosing a level.
  a brochure site: L1
    - every application starts at L1, the floor
  the online store: L2
    - every application starts at L1, the floor
    - it holds customer accounts or personal data, so L2
  the online bank: L3
    - every application starts at L1, the floor
    - it holds customer accounts or personal data, so L2
    - it moves money, is regulated and holds highly sensitive data, so L3
  of 14 requirements, L1 applies 8, L2 applies 12 and L3 applies 14: each level includes the ones below it
TWO. Requirements written down as data.
  security-requirements.tsv holds 14 requirements, and reads back the same: true
  for example SR-01 (Web Frontend Security, L1, automated): Every page sets a content security policy, nosniff and a framing policy
  verified by an automated test: 6, by a configuration check: 4, by a person: 4
  the statements are the team's own words and the ids are the team's own; each one names its chapter of ASVS
THREE. Checks that ask the running store.
  does a page carry a CSP, nosniff and a framing policy: pass
  is the session cookie Secure and HttpOnly: pass
  is a password kept as a slow, salted hash: pass
  does sign-in issue a new session id: pass
  does an error page hide the stack trace: pass
  is the debug endpoint closed: pass
  is the oldest TLS version allowed 1.2 or later: pass
  do staff sign in with a second factor: FAIL
  are security events logged: pass
  are account pages marked no-store: pass
  9 of 10 checks pass on the store as it is configured today
  the same password check on a build that stores passwords as plain SHA-256: FAIL  <- A CHECK CATCHES WHAT A REVIEW MIGHT MISS
