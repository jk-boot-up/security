ONE. The system as a data-flow model.
  the bank: 2 external entities, 3 processes, 2 data stores, 8 flows and 3 trust boundaries
  internet boundary (device | dmz): crossed by F2
  gateway boundary (dmz | internal): crossed by F3, F8
  partner boundary (internal | partner): crossed by F6, F7
  problems in the model: 0
  an earlier draft, where the app writes card numbers straight into a card vault: 2 problems
    D1 goes from device to internal with no single boundary between them: it skips a boundary, or one is missing from the picture
    S3 card vault has no owner
  a picture that skips a boundary hides the threats that live on it, so the model is checked before it is used
TWO. STRIDE per element: questions nobody forgets to ask.
  the rules find 20 candidate threats: S 4, T 5, R 4, I 2, D 1, E 4
  TH-01 S:E1 spoofing: someone pretends to be the customer
  TH-05 T:F2 tampering: the payment request with token is changed between the mobile app and the API gateway, across the internet boundary
  TH-11 R:F3 repudiation: whoever sent the authorized payment through the API gateway later denies sending it
  TH-14 I:S1 information disclosure: the accounts database is read by someone who should not see it
  TH-16 D:P2 denial of service: the API gateway is flooded until customers cannot pay
  TH-19 E:F7 elevation of privilege: a caller from the partner zone gains the rights of the payments service
  each category is the opposite of a property: spoofing against authenticity, tampering against integrity, and so on
THREE. Rating and deciding.
  highest risk: E:F2 likelihood 5 x impact 5 = 25 (a caller from the device zone gains the rights of the API gateway)
  highest risk: R:F2 likelihood 5 x impact 5 = 25 (whoever sent the payment request with token through the mobile app later denies sending it)
  highest risk: T:F2 likelihood 5 x impact 5 = 25 (the payment request with token is changed between the mobile app and the API gateway, across the internet boundary)
  decisions: mitigate 17, accept 1, transfer 1, avoid 1
  accepted R:F6, the processor's signed receipts and the contract cover disputes; owner payments lead, review on day 90
  transferred D:P2 to the hosting provider's denial-of-service protection, under contract
  avoided I:S2: card numbers and secrets are never written to the audit log
  undecided threats: 0
FOUR. Mitigations as tests.
  8 checks; every mitigation names one: true
  checks failing on the bank as built: 0
  a design change adds F9: the payments service sends refunds to the card processor, unencrypted
  checks failing now: 1
    TLS on every flow that crosses a boundary: F9 refund is not encrypted  <- THE TEST FAILS BEFORE THE RELEASE
  new threats with no decision: 2 (T:F9, R:F9)
  the earlier draft fails 3 checks, so it would never have shipped either
FIVE. The bill, and the habit.
  the model is 7 elements, 8 flows and 20 threats: small enough to read in one sitting, and to keep up to date
  today is day 120; accepted risks past their review day: 1  <- AN ACCEPTED RISK IS A DECISION WITH AN EXPIRY DATE
  review the model when a flow, a store, a boundary or a third party is added, not once a year
  four questions, every time: what is being built? what can go wrong? what is being done about it? was it done well enough?
  the rules only find candidates: people still judge likelihood, impact and the right control
