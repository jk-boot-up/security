# Attack Trees and Abuse Cases in Threat Dragon, Explained

## The idea in one sentence

A threat model file is a diagram with threats pinned to it; the file is only worth what is true of the system.

## The 5 acts

### 1. The tree, as a Threat Dragon model

The attack tree of the plain project: the cheapest way in costs 50 EUR via B1, some way works with a chance of 97%, and there are 8 abuse cases. The model file for Threat Dragon 2.6.2 has one diagram of 13 cells: 2 trust boundaries, 2 actors, 3 processes, 1 store and 5 flows, and 8 threats, all Open. Each abuse case is a threat on the element or flow it hits, with a STRIDE type, a severity (High if it is cheap or likely, Medium up to 5,000 EUR, Low beyond) and a score such as cost 50 EUR, chance 90%. The tree's AND and OR stay in the plain project, because a model of flat threats has no place for them.

### 2. Checked by Threat Dragon's own validator

The image carries the schema in its editor bundle and the Ajv that checks it; both are used as they are. The bank's model is valid. With no summary title it is refused: .summary should have required property 'title'. With a diagram type that is too short: should NOT be shorter than 3 characters. With a cell that has no id: should have required property 'id'. With a size of 5: should be >= 10. The editor refuses a file that fails these checks when it is opened, so a file generated by a program is checked the same way before anyone opens it.

### 3. The plan, step by step, in the file

Step 0 has 8 open threats in the file and 8 abuse cases failing; after OWN, 7 and 7; after CSRF, 6 and 6; after PASSKEY, 3 and 3; after CSP, 2 and 2. Every file is valid for the editor. After the plan the threats AC1 to AC6 are Mitigated, each naming the defence in place; still open are AC7 and AC8, the insider and the library flaw, as in the plain project. The file and the tests agree because both come from the same configuration; the file is the picture of the tests, and it is what a reviewer opens.

### 4. Checks the schema cannot make

Rules over the file: complete threats, known status and severity, a STRIDE type, a mitigated threat names its defence, the open flag of a cell matches its threats, flows end at cells that exist, threatTop is the highest number, and every abuse case has a threat. The model before the plan has 0 problems and so has the model after. A mitigated threat with an empty mitigation breaks mitigated-names-its-defence; a cell whose hasOpenThreats is false while it has an open threat breaks open-flag-matches-threats; a flow whose target is not a cell breaks flow-ends-exist; threatTop of 3 against a highest number of 8 breaks threat-top-is-highest-number.

### 5. The editor, and the bill

The editor's server started from the image, with generated keys, on a loopback port: health 200, the page 200 titled OWASP Threat Dragon. The providers it offers are only a local session: bitbucket, github, gitlab and google are all disabled. Its model API without signing in answers 401; a model is opened in the browser from a file, in a local session, and saved back to a file or a repository. The threats are flat and typed by STRIDE: cost, chance and the AND and OR of the tree live in the description and the score text. Threat Dragon stores no tests: whether a Mitigated threat is true is what the abuse cases in the code say.

## The verdict

Generate the model from the thing you can test, validate it with the editor's schema, add rules for what the schema cannot say, keep it in version control, and let the abuse cases in the code decide whether a threat is Mitigated.

## How to recognise this in code you did not write

- A `threat-model.json` file with `diagrams` and `cells`.
- A threat with `status`, `severity` and `mitigation`.
- `tm.Process` and `tm.Flow` in a JSON file.
- A "Local Session" button on a login page.

## Where you have already met this

- A threat model JSON file in a repository.
- A diagram with red numbers on the flows.
- A status column with Open, Mitigated and N/A.
- A "Report" button in a threat modeling tool.
