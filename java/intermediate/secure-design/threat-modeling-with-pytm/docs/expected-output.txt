ONE. The bank, written for pytm.
  the design: 7 elements, 8 flows and 4 boundaries, written by the program as 66 lines of Python for pytm 1.4.0
  the first lines of the model:
    from pytm import TM, Actor, ExternalEntity, Process, Server, Datastore, Dataflow, Boundary
    tm = TM("Bank payments")
    tm.description = "The online bank: a mobile app, an API gateway, a payments service, two stores and a card processor"
    tm.isOrdered = True
    device = Boundary("Device")
    partner = Boundary("Partner")
  pytm's library has 113 threats, each with a condition over the answers given about an element or a flow
  the draft of the plain project, with a card vault and a flow from the app that skips a boundary: pytm runs it without a complaint, and reports 9 findings about the new store and flow
  the plain project's model check reported 2 problems for the same draft: pytm judges the answers about each element, not the shape of the picture
TWO. What pytm finds when nothing is said.
  170 findings from 73 different threats; by severity: {Very High=16, High=59, Medium=85, Low=8, Very Low=2}
  per element or flow: {API gateway=44, Accounts database=4, Audit log=4, Authorized payment=5, Balance update=5, Card charge=5, Charge result=5, Login and payment request=5, Mobile app=34, Payment record=5, Payment request with token=5, Payments service=44, Request record=5}
  the most severe, in order:
    Very High AC06   API gateway          Using Malicious Files
    Very High AC06   Payments service     Using Malicious Files
    Very High AC14   Mobile app           Catching exception throw/signal from privileged block
    Very High AC17   API gateway          Session Hijacking - ServerSide
    Very High AC17   Payments service     Session Hijacking - ServerSide
    Very High AC18   Mobile app           Session Hijacking - ClientSide
  the plain project's STRIDE rules gave 20 candidates for the same bank; pytm checks each of its 113 threats against every element and flow it applies to, and starts from the worst case when nothing is said
THREE. Every answer changes the findings.
  NONE              170 findings  (no answers: every default is the worst case)
  ENCRYPTION        167 findings, 3 gone  (traffic and stores are encrypted)
  AUTHENTICATION    159 findings, 8 gone  (callers and services are authenticated)
  ACCESS_AND_INPUT  111 findings, 48 gone  (access control, least privilege and input handling)
  RESILIENCE         94 findings, 17 gone  (hardening, limits and logging)
  the findings are a function of the answers: an answer that is not true makes a finding disappear, which is why each answer needs an owner and a test
FOUR. A diagram and a report.
  --dfd writes a graph for Graphviz; rendered, the picture has 7 nodes, 8 arrows and 4 trust boundaries
  --report fills a template of our own: 94 findings listed, each with its element and severity, from 102 lines of Markdown
  the diagram and the report come from the same model as the findings, so they cannot disagree with it
FIVE. The bill.
  a design change, refunds sent to the card processor over plain http: 94 findings become 99, 5 of them about the new flow  <- THE MODEL CATCHES THE CHANGE ONLY IF THE MODEL IS CHANGED
  findings that mention XML in a bank that parses none: 5; a library of generic threats gives candidates, and a person says which apply
  pytm holds no decision: no owner, no accept or transfer, no review date, no check that a mitigation exists; those stay in the register of the plain project
  the Python model is a second copy of the design: here it is written from the Java design so that there is one, and it is regenerated with every change
  the answers are the team's claims about the system: a claim that is not tested is a finding that is hidden
