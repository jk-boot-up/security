ONE. Where validation belongs.
  THE REQUEST, SENT WITHOUT THE PAGE:
    cart         SHO-1042 x -3
    fields       email, country, postalCode, login, lines
                 (no price field: the catalogue has the price)
  BEFORE THE FIX (a shop that trusts the page):
    total        89.90 x -3 = -269.70  <- A REFUND
  AFTER THE FIX (constraints on the service's parameter):
    cart -3      place.checkout.lines[0].quantity
                 must be greater than or equal to 1
    no form      place.checkout: must not be null
    honest       accepted, 89.90 x 2 = 179.80
  HOW THE PATH place.checkout.lines[0].quantity IS BUILT:
    place        method
    checkout     parameter
    lines        property
    quantity     property, element 0 of the list before it
    message      from @Min(1) on Line.quantity
TWO. Say what is allowed, in annotations.
  THE RULES, WRITTEN ON THE RECORDS:
    quantity     @Min(1) @Max(99)
    sku          @NotNull @Pattern([A-Z]{3}-\d{4}) @InStock
    email        @NotBlank @Size(max=254) @Email
    country      @NotNull @Country
  QUANTITY (THE INPUT, THEN THE RESULT):
    7                    accepted
    0                    refused: must be greater than or equal to 1
    100                  refused: must be less than or equal to 99
  SKU:
    "SHO-1042"           accepted
    "sho-1042"           refused: must match "[A-Z]{3}-\d{4}"
    "SHO-1042;"          refused: must match "[A-Z]{3}-\d{4}"
  EMAIL:
    "Ben@Shop.EXAMPLE"   accepted
    "ben@@shop.example"  refused: must be a well-formed email address
    "ben@localhost"      accepted  <- WIDER THAN THE SHOP NEEDS
  COUNTRY:
    "DE"   accepted
    "ZZ"   refused: a two-letter country code such as IN or DE
    "de"   refused: a two-letter country code such as IN or DE
  THE INPUT, A FORM WITH SEVERAL BAD FIELDS:
    email        ben@@shop.example
    country      ZZ
    login        Ben K
    cart         sho-1042 x 0
  THE RESULT, 5 PROBLEMS AT ONCE:
    country: a two-letter country code such as IN or DE
    email: must be a well-formed email address
    lines[0].quantity: must be greater than or equal to 1
    lines[0].sku: must match "[A-Z]{3}-\d{4}"
    login: must match "[a-z0-9._-]+"
THREE. Your own constraints, across fields, and in an order.
  THE INPUT, FIVE LOGINS:
    ben[U+200B]k      a zero-width space
    ben[U+000A]k      a line break
    BenK              capitals
    b[U+0435]n.k      Cyrillic е in place of e
    jose[U+0301]      é typed as two characters
  THE RESULT:          @NoInvisible  all the login's rules
    ben[U+200B]k      refused       refused
    ben[U+000A]k      refused       refused
    BenK              accepted      refused
    b[U+0435]n.k      accepted      refused
    jose[U+0301]      refused       refused
    caught       3 of 5 by @NoInvisible, 5 of 5 by all the rules
  THE INPUT, A RULE ACROSS TWO FIELDS:
    DE 1011      DE codes match \d{5}
    IN 110001    IN codes match \d{6}
  THE RESULT, ON THE POSTAL CODE:
    DE 1011      postalCode: not a postal code of that country
    IN 110001    accepted
  HOW THE GROUPS ORDER THE CHECKS (each runs if all before passed):
    1 Limits     sizes, before anything looks inside
    2 Default    shapes: @Pattern, @Email, @Min ...
    3 Expensive  @InStock: a catalogue lookup
  THE INPUT, TWO PRODUCT CODES:
    sho-1042     the wrong shape
    SHO-9999     the right shape, but not sold
  THE RESULT:
    sho-1042     0 lookups: must match "[A-Z]{3}-\d{4}"
    SHO-9999     1 lookup:  not in the catalogue
FOUR. Limits are validation too.
  THE INPUT, TWO OVERSIZED VALUES:
    cart         10000 lines
    e-mail       10013 characters
  THE RESULT, STOPPED IN THE Limits GROUP:
    cart         lines: size must be between 0 and 50, 0 lookups
    e-mail       email: size must be between 0 and 254
  BEFORE THE FIX, ((a+)+)+b ON n a's AND A !:
    8 a's        2264 steps
    12 a's       36808 steps  (x 16.3)
    16 a's       589752 steps  (x 16.0)
    4 more a's: about 2^4 = 16 times the work  <- ReDoS
  AFTER THE FIX, @Size(max = 20) IN THE Limits GROUP:
    5000 a's     code: size must be between 0 and 20, 0 steps
  WHY TWO LEVELS: THE JDK ON THE SIMPLER (a+)+$:
    8 a's        109 steps
    16 a's       349 steps  (x 3.2)
    32 a's       1213 steps  (x 3.5)
    twice the a's, 3 to 4 times the work: not doubling per a
FIVE. The bill: what validation does not do.
  THE INPUT, A REVIEW TITLE:
    title        <b>great</b> (12 characters)
  THE RESULT, A MESSAGE THAT REPEATS THE VALUE:
    title: '<b>great</b>' is not 3 to 10 characters
    repeats it?  true  <- MARKUP IN AN ERROR MESSAGE
  THE INPUT, A COUPON PUT INTO A MESSAGE TEMPLATE:
    ${1+1}
    ${'a'.concat('b')}
  BEFORE THE FIX (templates may call methods, as old versions did):
    ${1+1}              the coupon 2 does not exist
    ${'a'.concat('b')}  the coupon ab does not exist
    the visitor's text was run as code  <- EXPRESSION INJECTION
  AFTER THE FIX:
    default      the coupon ${1+1} does not exist
    parameter    the coupon ${1+1} does not exist
  SO:
    valid text still needs encoding on output and query parameters;
    each rule is a business decision, written down
