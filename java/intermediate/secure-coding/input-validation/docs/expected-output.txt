ONE. Where validation belongs.
  the checkout page refuses a quantity of -3 before sending: true
  the same request sent without the page, to a shop that trusts the page: total -269.70  <- A NEGATIVE TOTAL IS A REFUND
  a hidden price field changed to 0.01: total 0.02 instead of 179.80  <- THE CUSTOMER SET THE PRICE
  the checkout that validates on the server: accepted false (quantity: digits only)
  and the hidden price: accepted false (price: not a field of this form)
  an honest order: accepted true, total 179.80 from the catalogue
TWO. Say what is allowed, and parse into types.
  quantity "7": accepted as 7
  quantity "0": refused (from 1 to 99)
  quantity "1e2": refused (digits only)
  quantity " 5": refused (digits only)
  sku "SHO-1042": accepted as SHO-1042
  sku "sho-1042": refused (three capital letters, a dash and four digits)
  sku "SHO-1042;": refused (longer than 8 characters)
  email "Ben@Shop.EXAMPLE": accepted as Ben@shop.example
  email "ben@@shop.example": refused (not a valid address)
  email "ben@localhost": refused (not a valid address)
  country "DE": accepted as DE
  country "ZZ": refused (a two-letter country code such as IN or DE)
  country "de": refused (a two-letter country code such as IN or DE)
  amount "19.50": accepted as 19.50
  amount "19.505": refused (digits with at most two decimals)
  amount "-5": refused (digits with at most two decimals)
  amount "NaN": refused (digits with at most two decimals)
  a form with four bad fields reports all four at once: 4
  each value that passes is a type that cannot hold anything else, so later code never checks it again
THREE. Canonicalise before validating.
  ana is registered; a registry that compares raw text also accepts the full-width ａｎａ: true  <- TWO ACCOUNTS FOR ONE NAME
  and ANA in capitals: true
  the canonical registry takes ana: true
  the canonical registry folds the full-width spelling to ana: refused (already taken)
  an invisible zero-width space inside a name: refused (no control or invisible characters)
  a line break inside a name: refused (no control or invisible characters)
  Cyrillic а in place of a: refused (3 to 20 letters, digits, dots, dashes or underscores); login names are kept to plain letters
  José typed two ways looks the same; as raw text equal: false, after NFC: true
  a display name "Shоp Suppоrt" with Cyrillic o: refused (reserved for the shop's staff); "José Martín": accepted
FOUR. Limits are validation too.
  a request body of 1000000 bytes: refused (larger than 16384 bytes) after reading 16385 of them
  a cart of 10000 lines: refused (more than 50 lines)
  an e-mail address of 10000 characters: refused (longer than 254 characters)
  the pattern (a+)+$ on 10 a's and a !: matched false after 2036 steps
  the pattern (a+)+$ on 15 a's and a !: matched false after 65519 steps
  the pattern (a+)+$ on 20 a's and a !: matched false after 2097130 steps
  each extra character roughly doubles the work  <- A FEW DOZEN CHARACTERS CAN STOP A SERVER (ReDoS)
  the same rule written without nesting, a+$, checked in one pass: 21 steps for 20 a's and a !
  so: no nested repetition in patterns that read input, and a length limit before any pattern runs
FIVE. The bill: what validation does not do.
  a review "<b>great</b>" is valid text, and still markup: valid is not the same as safe to put in a page, so encode it on output (see cross-site-scripting)
  a surname O'Brien is valid and contains a quote, so the database layer must bind values as parameters, never paste them into query text
  a refused e-mail address with a line break and markup: "email: not a valid address", raw input repeated: false
  a wholesale order of 150: refused (from 1 to 99); a limit stricter than the business turns customers away, so each rule is a written business decision
  validation narrows what reaches the code; encoding, parameters and access checks still do their own jobs
