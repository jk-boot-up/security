ONE. Check, then act: two requests in the gap.
  THE REQUESTS (ANA-1 holds 100, in PostgreSQL 18):
    A and B      withdraw 80 each, on two connections at once
    each         selects the balance, checks it in Java, updates
  THE STEPS (A reads, B reads, A writes, B writes):
    A reads      100, checks 100 >= 80: true
    B reads      100, checks 100 >= 80: true
    A writes     balance = 20 (100 - 80), commits
    B writes     balance = 20 (100 - 80), commits
  THE RESULT:
    paid out     160 from a balance of 100  <- BOTH CHECKS PASSED
    balance      20
  AFTER THE FIX, ONE: THE RULE IN THE TABLE:
    column       balance int check (balance >= 0)
    update       set balance = balance - 80
    A            100 - 80 = 20: paid
    B            20 - 80 = -60 < 0: 23514 check_violation
    paid out     80, balance 20
  AFTER THE FIX, TWO: THE CHECK INSIDE THE UPDATE:
    update       ... where id = 'ANA-1' and balance >= 80
    A            1 row changed: paid
    B            0 rows changed (20 >= 80 is false): refused
    paid out     80
  A SINGLE-USE COUPON SPRING20, 20 OFF (BEFORE THE FIX):
    A, B read    used = false and false
    discount     20 + 20 = 40  <- USED TWICE
  AFTER THE FIX: CLAIMED IN ONE STATEMENT:
    update       set used = true where ... and used = false
    A            1 row: claimed, gets 20 off
    B            0 rows: already used, refused
TWO. Row locks: making the check and the write one step.
  THE STEPS (select ... for update):
    A            locks the row ANA-1 and reads 100
    B            asks for the same row: waiting true
    A            pays out 80 and commits: the lock is released
    B            gets the row, reads 20, 20 >= 80: false, refuses
  THE RESULT:
    paid out     80, balance 20
  WHEN B SHOULD NOT WAIT (A HOLDS THE ROW):
    nowait       refused at once: 55P03 lock_not_available
    timeout      lock_timeout 300 ms, waited it: true, gave up: 55P03
    skip locked  takes the next free row: BEN-2 true
THREE. Isolation levels.
  READ COMMITTED (THE DEFAULT), EACH TAKES 30:
    A reads      100
    B            takes 30 and commits: 70
    A updates    balance - 30 on the new value: 70 - 30 = 40
  REPEATABLE READ, THE SAME STEPS:
    A reads      100, and keeps that snapshot
    B            takes 30 and commits: 70
    A updates    refused: 40001 serialization_failure
    message      could not serialize access due to concurrent update
    A retries    from the start (1 attempt): 70 - 30 = 40
  ONE RULE OVER TWO ROWS (ANA-1 100, ANA-2 100, TOTAL >= 0):
    A and B      each read the total, then take 150 from one row
  BEFORE THE FIX: REPEATABLE READ:
    A and B see  total 200 and 200: room for 150 each
    A            takes 150 from ANA-1, commits
    B            takes 150 from ANA-2, commits
    total        200 - 150 - 150 = -100  <- WRITE SKEW
  AFTER THE FIX: SERIALIZABLE:
    A and B see  total 200 and 200: room for 150 each
    A            takes 150 from ANA-1, commits
    B            refused: 40001 serialization_failure
    total        200 - 150 = 50
FOUR. Optimistic locking with Hibernate, and one-time keys.
  BOTH LOAD THE ACCOUNT (Hibernate 7, a @Version column):
    A            balance 100, version 0
    B            balance 100, version 0
  A PAYS 80 (true) AND COMMITS:
    sql          update hib_account set balance=?,version=?
                 where id=? and version=?
    values       balance 20, version 0 + 1 = 1, where version = 0
  B PAYS 80 (true) ON WHAT IT LOADED, AND COMMITS:
    where        version = 0, but the row is at 1: 0 rows
    commit       refused: OptimisticLockException
    B retries    loads 20 at version 1, 20 >= 80: false
  A PESSIMISTIC WRITE LOCK FROM HIBERNATE SENDS:
    sql          select ... for no key update of ha1_0
  ONE PAYMENT KEY, SENT TWICE AT ONCE (KEY IS THE PRIMARY KEY):
    A            inserts rent-october: 1 row, moves 70
    B            inserts the same key: waits for A true
    A            commits the key and the money together
    B            0 rows: the key is taken, nothing moves
    ana          100 - 70 = 30
FIVE. The bill.
  TWO TRANSFERS, EACH LOCKING ITS OWN SENDER FIRST:
    A            locks ANA-1, then asks for BEN-2
    B            locks BEN-2, then asks for ANA-1
    PostgreSQL   finds the cycle, cancels 1: 40P01 deadlock_detected
    the other    done  <- RETRY THE CANCELLED ONE
  AFTER THE FIX: ONE LOCK ORDER (ORDER BY ID ... FOR UPDATE):
    A and B      done and done
  TWO SERVERS, EACH WITH A LOCK IN ITS OWN MEMORY:
    paid out     80 + 80 = 160 from 100  <- THE LOCKS NEVER MEET
  A ROW LOCKED WHILE A PERSON CONFIRMS:
    B            gave up after 300 ms: 55P03  <- KEEP IT SHORT
  WHAT EACH ERROR CODE ASKS OF THE APPLICATION:
    23514  check_violation        refuse, do not retry
    55P03  lock_not_available     try again later
    40001  serialization_failure  retry the transaction
    40P01  deadlock_detected      retry the transaction
