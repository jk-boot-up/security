ONE. An endpoint that trusts whatever is posted to it.
  THE REQUEST (posted by anyone, with no signature):
    POST /webhooks/payments
    {"id":"evt_forged1","type":"payment.succeeded",
    "order":"A-1001","amount":4200}
  THE RESPONSE:
    200 order A-1001 is now paid
  THE PROVIDER'S OWN RECORDS FOR A-1001:
    no payment  <- MARKED PAID, NEVER PAID
  the address is public: a message to it proves nothing
TWO. How the provider signs a message.
  THE INPUTS:
    secret  whsec-demo-shop-2026  (20 bytes, shared)
    time t  1800000000  (seconds since 1 January 1970)
    raw body (79 bytes):
      {"id":"evt_1001paid","type":"payment.succeeded",
      "order":"A-1001","amount":4200}
  STEP 1, WHAT IS SIGNED: t, a dot, the raw body
    1800000000.{"id":"evt_1001paid","type":"payment.succeeded",
    "order":"A-1001","amount":4200}
  STEP 2, THE KEY PADDED WITH ZEROS TO 64 BYTES, THEN MIXED:
    padded key   77 68 73 65 63 2d 64 65 ...
    XOR 36 each  41 5e 45 53 55 1b 52 53 ...  inner key
    XOR 5c each  2b 34 2f 39 3f 71 38 39 ...  outer key
  STEP 3, TWO SHA-256 HASHES:
    inner = SHA-256(inner key + what is signed)
          = 3f6f142eb2d9aa2755f74c1540b0e948
            0685dff163afa27ff975ff5ea5f93936
    v1    = SHA-256(outer key + inner)
          = dc14c6ef9d7ef5d1fd993788607f660a
            df0d0e8e177d6a0e2f5748dcce6c5cc3
  THE HEADER SENT WITH THE BODY (Shop-Signature):
    t=1800000000,
    v1=dc14c6ef9d7ef5d1fd993788607f660a
       df0d0e8e177d6a0e2f5748dcce6c5cc3
  the same as the JDK's Mac HmacSHA256: true
THREE. The store checks the signature.
  THE STORE'S STEPS:
    read t and v1 from the header
    compute the HMAC of t, a dot and the raw body received
    compare it with v1 in constant time (MessageDigest.isEqual)
  THE MESSAGES AND RESPONSES:
    1 the real event, as signed
      v1 sent dc14c6ef9d7ef5d1...  computed dc14c6ef9d7ef5d1...
      200 order A-1001 is now paid
    2 the body changed to A-1002, the same header
      v1 sent dc14c6ef9d7ef5d1...  computed 8dfb52122bf9f611...
      401 refused: the signature does not match
    3 a forged event with no header
      400 refused: no signature
    4 a forged event signed with another secret
      v1 sent c45635178c433d5b...  computed dab5c7f482e4636c...
      401 refused: the signature does not match
  THE SAME OVER THE LOCAL HTTP SERVER (POST only, 4096 bytes):
    1 real 200, 2 changed 401, 3 no header 400
FOUR. A real message sent again.
  THE MESSAGE (a real refund, t=1800000000):
    {"id":"evt_1001refund","type":"payment.refunded",
    "order":"A-1001","amount":4200}
  WITH SIGNATURES ONLY:
    the real refund, at t + 0 seconds:
      200 order A-1001 is now refunded, 4200 cents paid back
    a copy, sent again at t + 3600 seconds:
      200 order A-1001 is now refunded, 4200 cents paid back
    refunds paid: 2, 8400 cents for a 4200-cent order  <- REPLAYED
  WITH A 300-SECOND WINDOW AND A RECORD OF EVENT IDS:
    the real refund, at t + 0 seconds:
      200 order A-1001 is now refunded, 4200 cents paid back
    the copy at t + 30 (age 30 <= 300, id already seen):
      200 already processed evt_1001refund, nothing changed
    the copy at t + 3630 (age 3630 > 300):
      400 refused: signed too long ago
    the copy with its t edited to 1800003630 (age 0):
      401 refused: the signature does not match
    refunds paid: 1, 4200 cents
  the time is signed too, so it cannot be changed
FIVE. The same event twice, out of order, and a new secret.
  THE EVENTS, IN THE ORDER THEY ARRIVE:
    1 evt_1001paid   A-1001 payment.succeeded
    2 evt_1001paid   A-1001 payment.succeeded  (a retry)
    3 evt_1002refund A-1002 payment.refunded  (before its payment)
    4 evt_1002paid   A-1002 payment.succeeded
    5 evt_1002refund A-1002 payment.refunded  (a retry)
  THE RESPONSES (event, the order's state before, reply):
    1 new  200 order A-1001 is now paid
    2 paid 200 already processed evt_1001paid, nothing changed
    3 new  409 not applied: order is new, try again later
    4 new  200 order A-1002 is now paid
    5 paid 200 order A-1002 is now refunded, 1999 cents paid back
  the orders changed 3 times; A-1001 is paid, A-1002 is refunded
  CHANGING THE SECRET, THE SECRETS THE STORE ACCEPTS:
    before      whsec-demo-shop-2026
    changeover  whsec-demo-shop-2026, whsec-demo-shop-2027
    after       whsec-demo-shop-2027
  THE MESSAGES AND RESPONSES:
    changeover, signed with whsec-demo-shop-2026:
      200 order A-1001 is now paid
    changeover, signed with whsec-demo-shop-2027:
      200 order A-1002 is now paid
    after, signed with whsec-demo-shop-2026:
      401 refused: the signature does not match
SIX. The bill.
  THE RAW BODY, AS SIGNED (79 bytes):
    {"id":"evt_1001paid","type":"payment.succeeded",
    "order":"A-1001","amount":4200}
  THE SAME EVENT, PARSED AND WRITTEN AGAIN (88 bytes):
    { "id": "evt_1001paid", "type": "payment.succeeded",
    "order": "A-1001", "amount": 4200 }
  THE RESPONSES (the header's v1 is dc14c6ef9d7ef5d1...):
    written again: computed v1 909d1bd03dc6ecc1...
      401 refused: the signature does not match
    raw body:      computed v1 dc14c6ef9d7ef5d1...
      200 order A-1001 is now paid
  THE PROVIDER'S API, ASKED BEFORE SHIPPING A-1001:
    payment.succeeded 4200, which matches the event
  keep the raw bytes, and check them before parsing
  keep the secret outside the code; change it on a schedule
  events come late, twice or out of order: handlers are idempotent
