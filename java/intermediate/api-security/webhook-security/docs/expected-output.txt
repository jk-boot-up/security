ONE. An endpoint that trusts whatever is posted to it.
  anyone posts {"type":"payment.succeeded","order":"A-1001"} to the store's webhook address, with no signature
  the store answers: 200 order A-1001 is now paid
  the provider's own records for A-1001: no payment  <- MARKED PAID, NEVER PAID
  the webhook address is public, so a message to it proves nothing about who sent it
TWO. A signature over the exact bytes.
  the provider signs HMAC-SHA256 of the timestamp and the raw body with the secret it shares with the store
  the real event, as signed: 200 order A-1001 is now paid
  the same signature on a body changed to order A-1002: 401 refused: the signature does not match
  a forged event with no signature: 400 refused: no signature
  a forged event signed with a secret that is not the provider's: 401 refused: the signature does not match
  the comparison takes the same time however many bytes match (MessageDigest.isEqual)
  the same checks over the local HTTP server: real event 200, changed body 401, no signature 400
THREE. A real message sent again.
  with signatures only, a real refund: 200 order A-1001 is now refunded, 4200 cents paid back
  someone who saw that message sends a copy an hour later: 200 order A-1001 is now refunded, 4200 cents paid back
  refunds paid for A-1001: 2, 8400 cents for a 4200-cent order  <- A REAL MESSAGE, REPLAYED
  with a 300-second window on the signed time, and a record of processed event ids:
    the real refund: 200 order A-1001 is now refunded, 4200 cents paid back
    the same message again after 30 seconds: 200 already processed evt_1001refund, nothing changed
    the same message again an hour later: 400 refused: signed too long ago
    the same message with its time edited to now: 401 refused: the signature does not match, because the time is part of what is signed
    refunds paid for A-1001: 1, 4200 cents
FOUR. The same event twice, events out of order, and a new secret.
  the provider retries the payment event, so it arrives twice: order changes 1 time, A-1001 is paid
  a refund for A-1002 arrives before its payment: 409 not applied: order is new, try again later
  then the payment: 200 order A-1002 is now paid
  then the provider's retry of the refund: 200 order A-1002 is now refunded, 1999 cents paid back
  changing the secret: the store accepts both for a while; a message signed with the old secret: 200, with the new one: 200
  after the old secret is removed, a message signed with it: 401 refused: the signature does not match
FIVE. The bill.
  a framework that parses the body and writes it again with other spacing, then checks the signature: 401 refused: the signature does not match
  so the raw bytes must be kept, and checked, before anything parses them
  the real event: 200 order A-1001 is now paid
  and before shipping, the store asks the provider's API about A-1001: payment.succeeded 4200, which matches the event
  the shared secret lives outside the code, is changed on a schedule with a changeover, and leaks are a forged-payment risk
  events can arrive late, twice or out of order, so every handler must be idempotent and check the order's state
