ONE. A profile call that works.
  THE REQUEST (Ana's app changes her display name):
    PATCH /accounts/acc-0001
    {"displayName": "Ana Ruiz"}
  THE RESPONSE (200, the account record itself):
    displayName       Ana Ruiz
    email             ana@bank.example
    role              customer
    balanceCents      125000
    creditLimitCents  50000
    riskScore         17
    cardNumber        4242 4242 4242 0001
    pinHash           pbkdf2$acc-0001$demo
  the app shows one field; the response carries 8
TWO. Whatever the caller sends becomes a field.
  THE REQUEST (two keys added by hand):
    PATCH /accounts/acc-0001
    {"displayName": "Ana",
     "role": "admin",
     "creditLimitCents": 100000000}
  THE RECORD BEFORE:
    role              customer
    creditLimitCents  50000
  THE RESPONSE (200, every key copied onto the record):
    role              admin  <- NOT HERS TO SET
    creditLimitCents  100000000  <- NOT HERS TO SET
  the API never decided which fields were hers
THREE. The response is the whole record, and a list has no end.
  THE REQUEST:
    GET /accounts/acc-0001
  THE RESPONSE (200, 8 fields, among them):
    cardNumber        4242 4242 4242 0001  <- FULL CARD
    pinHash           pbkdf2$acc-0001$demo  <- PIN HASH
    riskScore         17  <- INTERNAL
  THE REQUEST:
    GET /accounts?page=0&size=1000000
  THE RESPONSE (200):
    300 accounts x 8 fields = 2400 values  <- EVERY CUSTOMER
  THE REQUESTS:
    1000 x GET /accounts/acc-0001, in a loop
  THE RESPONSES:
    1000 answered with 200, none slowed down
FOUR. Explicit models and a page cap.
  THE REQUEST (the same two keys added by hand):
    PATCH /accounts/acc-0001
    {"displayName": "Ana",
     "role": "admin",
     "creditLimitCents": 100000000}
  THE CHECK (UpdateProfileRequest names displayName, email):
    displayName       named
    role              not named  <- UNKNOWN
    creditLimitCents  not named  <- UNKNOWN
  THE RESPONSE:
    400 unknown field
  THE RECORD AFTER (nothing changed):
    role              customer
    creditLimitCents  50000
  THE REQUEST (a field the model names):
    PATCH /accounts/acc-0001
    {"displayName": "Ana Ruiz"}
  THE RESPONSE (200, an AccountView with 5 fields):
    id                acc-0001
    displayName       Ana Ruiz
    email             ana@bank.example
    balanceCents      125000
    cardLast4         0001  (the app shows ****0001)
  THE REQUEST:
    GET /accounts/acc-0001
  THE RESPONSE (200):
    the same 5 fields; no card number, no PIN hash
  THE REQUEST:
    GET /accounts?page=0&size=1000000
  THE PAGE SIZE (capped at 50):
    min(1000000, 50) = 50
  THE RESPONSE (200, a DirectoryEntry per account):
    50 accounts x 2 fields (id, displayName)
    acc-0001  Ana Ruiz
    acc-0002  user2
    ... 48 more
FIVE. The budget runs out, and refills.
  THE BUDGET (one bucket of read tokens per caller):
    holds 100 tokens, refills 100 a minute = 1.67 a second
    one account costs 1 token; a list costs 1 per row
  ANA'S TOKENS BEFORE THE LOOP:
    100 - 1 (one account) - 50 (a page of 50) = 49
  THE REQUESTS:
    1000 x GET /accounts/acc-0001, in a loop
  THE RESPONSES:
    49 answered with 200
    951 refused with 429, Retry-After: 1
  HOW Retry-After IS WORKED OUT:
    tokens 0.00, a call costs 1, refill 1.67 a second
    wait = ceil((1 - 0.00) / 1.67) = ceil(0.60) = 1 second
  THE REQUEST, 1 SECOND LATER:
    GET /accounts/acc-0001
  THE RESPONSE:
    200; tokens 0.00 + 1.67 = 1.67, minus 1 = 0.67 left
  ANOTHER CUSTOMER MEANWHILE (user2, own bucket):
    GET /accounts?size=5 -> 200, 5 accounts; 95 tokens left
