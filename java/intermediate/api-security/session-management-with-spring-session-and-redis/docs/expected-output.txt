ONE. The session lives in Redis, which must be protected.
  THE REQUEST (redis-cli, no password): PING
  THE ANSWER: NOAUTH (refused)
  THE SIGN-IN RESPONSE (a real Spring Boot server):
    status 200
    Set-Cookie: __Host-session=<cookie>; Path=/; Secure;
        HttpOnly; SameSite=Strict
    problems found: 0
  THE ACCOUNT PAGE, WITH THAT COOKIE: status 200
  WHAT REDIS HOLDS NOW (the id shown as <id>):
    spring:session:expirations:<time>
    spring:session:index:PRINCIPAL_NAME_INDEX_NAME:ana
    spring:session:sessions:<id>
    spring:session:sessions:expires:<id>
  THE FIELDS OF spring:session:sessions:<id>:
    creationTime, lastAccessedTime
    maxInactiveInterval, sessionAttr:SPRING_SECURITY_CONTEXT
  HOW THE COOKIE IS MADE (an example id; real ones are random):
    the id, 36 characters: 3f2a7c1e-9b4d-4e8a-a6f0-5c1d2e3b4a90
    the first 3 characters, 3f2, are the bytes 33 66 32
    6 bits a character: 001100=M 110110=2 011000=Y 110010=y
    its Base64, 48 characters:
      M2YyYTdjMWUtOWI0ZC00ZThhLWE2ZjAtNWMxZDJlM2I0YTkw
    ana's real cookie is the Base64 of her Redis id: true
  THE REQUEST (a stolen copy of Redis's 1 session keys, as cookies):
  THE ANSWER: 1 sessions opened  <- REDIS HOLDS LIVE IDS
  the plain project kept a hash; here Redis needs a password,
  the loopback address only, and short timeouts
TWO. A new id at every sign-in.
  BEFORE ANA SIGNS IN:
    a stranger opens /welcome and gets the cookie <planted>
    and puts <planted> into ana's browser
  AFTER SIGN-IN, A BANK THAT KEEPS THE ID (fixation none):
    ana's cookie is still <planted>: true
    the stranger sends <planted>: allowed  <- SESSION FIXATION
  AFTER SIGN-IN, THE DEFAULT (changeSessionId):
    ana's cookie is still <planted>: false; she now has <new>
    the stranger sends <planted>: refused (401)
    ana sends <new>: allowed
    <planted> is a live record in Redis: false
THREE. How long a session lives.
  THE SETTINGS:
    idle timeout      2 seconds (spring.session.timeout, short
                      for the demo)
    absolute timeout  8 hours (a filter of our own)
  WHAT REDIS DOES WITH THE IDLE TIMEOUT:
    the record's time to live, at most 2 + 300 = 302 seconds: true
  IDLE (seconds since ana's last request -> the answer):
    1   -> allowed
    2.5 -> refused (401)
    the dead record is still in Redis: true; live records: 0
  ABSOLUTE (ana stays busy; the bank's clock is moved forward):
    7:59 after sign-in -> allowed
    8:01 after sign-in -> refused (401)
    created + 8:00 is before now, so the filter ends it
FOUR. Signing out, everywhere, and the limit.
  THE SIGN-OUT RESPONSE:
    status 200
    the browser is told to forget the cookie (Max-Age=0): true
    the record is still live in Redis: false
  A COPY MADE BEFORE SIGN-OUT, SENT AGAIN:
    refused (401)  <- THE SERVER ENDED THE SESSION
  ANA IS SIGNED IN ON HER PHONE, LAPTOP AND TABLET:
    live records in Redis: 3; in her index: 3
  SIGN OUT EVERYWHERE (from the laptop):
    200 ended 3 sessions
    the phone: refused (401); the tablet: refused (401)
  A PASSWORD CHANGE ON THE LAPTOP:
    200 ended 2 other sessions
    the laptop's new id: allowed; its old id: refused (401)
    the phone: refused (401)
  A LIMIT OF 3, THEN A FOURTH SIGN-IN ON HER WATCH:
    status 200
    the phone, the oldest: refused (401)
    the laptop: allowed; the watch: allowed
FIVE. The bill.
  THE REQUEST: ana signs in on server A; the next lands on B
  THE ANSWER FROM B, EACH SERVER WITH ITS OWN STORE:
    refused (401)  <- NEEDS A SHARED STORE
  THE ANSWER FROM B, BOTH USING THE SAME REDIS:
    allowed; and back on A: allowed
  WHILE REDIS STOPS ANSWERING:
    a request with a valid cookie: refused (500)
    a sign-in: refused (500)  <- FAILS CLOSED
  AFTER REDIS ANSWERS AGAIN:
    the same cookie: allowed
  20 REQUESTS FROM STRANGERS WITH NO COOKIE (records in Redis):
    request cache on, the default: 20  <- A STRANGER CAN FILL REDIS
    request cache off: 0
  THE PRICE:
    a customer who stops to read a statement signs in again
    and every request now needs Redis to answer
