ONE. An app that trusts the device.
THE DEVICE'S ROOTS (what the phone trusts):
  Public Root CA      shipped with the phone
  Helpful Proxy Root  added by a proxy, a tool or malware
THE CHAINS (leaf first, as each server sends it):
  genuine       api.bank.example <- Public Issuing CA
  interception  api.bank.example <- Helpful Proxy CA
THE CHECK, BY HAND (signed by a root on the phone?):
  genuine       yes, by Public Root CA
  interception  yes, by Helpful Proxy Root
THE RESULT (the app has no pins):
  genuine       ACCEPTED
  interception  ACCEPTED  <- THE PROXY READS IT ALL
TWO. An app that pins the server's key.
THE INPUT (the leaf's public key, EC P-256):
  SubjectPublicKeyInfo  91 bytes = 26 header + 65 point
THE PIN, WORKED OUT:
  SHA-256 of the 91 bytes  32 bytes  2f3abf264f56...
  Base64 of the hash  44 chars, the pin:
    Lzq/Jk9WKkUdfAIkFfeRw+9Of4eKCEcGlfwZSm7fewM=
THE BASE64, BY HAND (3 bytes -> 4 letters of 6 bits):
  bytes    2f 3a bf
  6 bits   001011 110011 101010 111111
  values   11     51     42     63
  letters  L      z      q      /
  32 bytes = 10 x 3 + 2 left -> 11 groups x 4 = 44 chars
  same as the JDK's Base64: yes
THE CHECK, BY HAND (is a key of the chain pinned?):
  genuine       yes, the leaf key Lzq/Jk9WKkUd...
  interception  none of 2 keys
THE RESULT (the app ships the leaf's pin):
  genuine                    ACCEPTED
  interception               REFUSED_BY_PIN
  interception, clean phone  REFUSED_BY_VALIDATION
THREE. The server renews with a new key.
THE RENEWAL (day 80: a new certificate, a new key):
  the app's pin      Lzq/Jk9WKkUd...
  the new key's pin  ZDwOX/eMCYca...
THE CHECK, BY HAND (is a key of the chain pinned?):
  renewed chain     none of 2 keys
THE RESULT (the app pinned to the old leaf key):
  renewed chain     REFUSED_BY_PIN  <- THE BANK'S OWN APP
THE FLEET, WORKED OUT (10000 installs, 85% update in a week):
  locked out on day 0   10000
  after a week          10000 - 10000 x 85 / 100 = 1500
FOUR. Pins chosen so that rotation does not break the app.
THE PINS (what each app ships):
  issuer pin     the Public Issuing CA's key eb8u2CB5PRIO...
  leaf + backup  the leaf key, and a spare kept offline
  report-only    the leaf key; a mismatch is only reported
THE CHECK, BY HAND (which key of the chain is pinned?):
  issuer pin, renewed       yes, the issuer's key eb8u2CB5PRIO...
  issuer pin, interception  none of 2 keys
  backup pin, key switched  yes, the backup key iJUyqyKML7H6...
  report-only, renewed      none of 2 keys
THE RESULT:
  issuer pin, renewed       ACCEPTED
  issuer pin, interception  REFUSED_BY_PIN
  backup pin, key switched  ACCEPTED
  report-only, renewed      ACCEPTED_REPORT_ONLY
  reports collected         1
FIVE. Why browsers stopped letting servers set pins.
THE HEADER (a meddler answers one first visit, HPKP):
  Public-Key-Pins: pin-sha256="uY0GG0fH8UUc...";
    pin-sha256="wwq5cMyuB4F8..."; max-age=31536000
THE max-age, WORKED OUT:
  31536000 s / 86400 s a day = 365 days
THE CHECK, BY HAND (is the visit within 365 days?):
  day 30   30 < 365: the meddler's pins still apply
  day 400  400 > 365: the pins have expired
THE RESULT (the genuine bank server):
  day 30   blocked for every returning visitor
  day 400  accepted again
THE SITE'S OWN PINS (leaf + backup), THEN A NEW KEY:
  day 80   blocked until day 365  <- NO WAY TO UNDO IT
