ONE. What the wire shows.
  a login to the shop over TLS 1.3, copied by a tap that sees only what a machine on the path sees, then read with tshark and no secrets
  the Client Hello names the shop in the clear: www.shop.localhost
  the Server Hello chooses: TLS_AES_256_GCM_SHA384
  the certificate is in the capture: false; HTTP requests tshark can read: 0; encrypted application data records: true
  the bytes of the capture contain the word password: false  <- THE PASSWORD IS THERE ONLY AS NOISE
  what a watcher learns anyway: the name, the times and the sizes
TWO. A key log: the secrets of one connection.
  openssl s_client -keylogfile wrote 5 lines, as a browser does when SSLKEYLOGFILE is set: [CLIENT_HANDSHAKE_TRAFFIC_SECRET, CLIENT_TRAFFIC_SECRET_0, EXPORTER_SECRET, SERVER_HANDSHAKE_TRAFFIC_SECRET, SERVER_TRAFFIC_SECRET_0]
  each line is a label, the connection's client random (32 bytes) and a secret (48 bytes), which ties it to one connection and nothing else
  the file holds no private key: true
THREE. The same capture, read with the key log.
  request: POST /login, form fields user,password = ana,hunter2
  response: 200, session=7f3a; Secure; HttpOnly, welcome ana
  the encrypted handshake opens too: the certificate is for www.shop.localhost  <- IN TLS 1.3 THE CERTIFICATE IS ENCRYPTED, AND THE KEY LOG OPENS IT
FOUR. A key log opens its own connection and no other.
  a second login, read with the first login's key log: 0 HTTP packets; with its own key log: opened
  one file with both logs opens both captures: true
  only the client's lines: requests opened: true, responses opened: false
FIVE. The server's own key is a different matter.
  the same login over TLS 1.2: the certificate is visible without any secret: true; over TLS 1.3 it is not: true
  recorded with ephemeral key exchange (ECDHE), then the server's private key leaks: HTTP packets opened: 0
  recorded with RSA key exchange, then the same kind of key leaks: opened, password hunter2  <- A LEAKED KEY OPENS EVERYTHING RECORDED BEFORE
  a key log is as good as the password it protects: where it is written, who can read it and when it is deleted are part of the bill
  nothing here needed a network card: the tap wrote the capture, because reading a card needs rights that a test should not ask for
