A container is a process with settings, so decide what a hijacked process can do before it happens: run as a non-root user, drop all capabilities, forbid new privileges, make the root file system read-only, keep the host out, and set limits; each setting removes specific attacks, and the Pod Security Standards name the levels.

An attacker who finds a flaw in the shop's application gets code execution inside the container. What they can do next depends on the container's settings, and the defaults are generous: a plain docker run gives root inside the container, 14 Linux capabilities, a writable file system, and no limits on memory or processes. Tutorials add more to "make it work": --privileged, the Docker socket, the host network. Each setting is a door for the attacker.

This project turns the question into code. A ContainerSpec holds the settings that matter (user, capabilities, privileged, read-only file system, privilege escalation, seccomp, host mounts and namespaces, memory and process limits, how secrets are passed, the image), and an attacker model asks thirteen questions of it: can a hijacked process read secrets, tamper with the app, drop and run a tool, become root, use dangerous system calls, sniff the network, mount host things, talk to the Docker socket, touch host files, reach the host network, see host processes, exhaust memory, fork without limit? Each answer names the setting that decides it.

What the project shows, in order: - Defaults: 7 of the 13 attacks are possible. The tutorial configuration: all 13. - Hardening one setting at a time, with the effect of each: host access, seccomp, capabilities, non-root user, no new privileges, read-only root, limits, down to 1 of 13. - Pod Security Standards: the Privileged, Baseline and Restricted levels, with the reasons a container fails the next level, and the same settings rendered as Docker flags and as a Kubernetes securityContext. - What is left: the application's own secrets. Hardening limits the blast radius; it does not make the application safe.

Maps to: OWASP Top 10 (2025) A02 Security Misconfiguration · CIS Docker and Kubernetes Benchmarks · Kubernetes Pod Security Standards · NIST SP 800-190 (Application Container Security) · CWE-250 · CWE-269.

The idea in everyday terms

A guest in a hotel room can do what the room allows: with the master key and the service lift (privileged, host mounts), they can reach every floor; with a plain key, only their room; with a room that has no phone line to the safe and a lock on the minibar, much less. You design the room for the day a guest turns out to be a thief.

The scenario

A containerised web shop with a flaw that gives an attacker code execution. The demo evaluates five configurations: Docker's defaults, the configuration from the tutorial, eight steps of hardening, the hardened container, and two settings that look harmless.

Run

./gradlew run

The demo tells the story in 5 acts, each printing exact numbers that the tests check:

Act What it shows
1. What 'docker run' with no options gives an attacker The input is Docker's defaults: root, 14 capabilities, a writable root, new privileges allowed, the default seccomp profile, no host access, no limits, secrets in the environment. The result: container 4 + kernel 1 + host 0 + resources 2 = 7 of 13 attacks possible, and the level is Baseline because the three Restricted checks fail.
2. The configuration from the tutorial The input is a command found in many tutorials: --privileged, unconfined seccomp, the host network and PID namespace, the Docker socket and /etc mounted. The result: 4 + 3 + 4 + 2 = 13 of 13 attacks possible, six reasons it is not even Baseline, so the level is Privileged.
3. One setting at a time Starting from 13 of 13: no host access 9, the default seccomp profile 8, drop all capabilities 6 (Baseline), a user that is not root 6 (blocks nothing alone), no new privileges 5 (Restricted), a read-only root with a noexec /tmp 3, memory and process limits 1: only read-secrets is left.
4. The hardened container The same settings as a docker run command and as a Kubernetes securityContext; all nine Pod Security checks pass, so the level is Restricted. The one attack left is read-secrets: the app must read its secrets, so a hijacked app can too.
5. Settings that look harmless Before: the hardened container, 1 of 13 and Restricted. Adding NET_RAW: still 1 of 13 (sniff-network stays blocked because the user is not root), but Baseline, as drops ALL capabilities now fails. Running as root with SYS_ADMIN: 3 of 13 (become-root and mount-host come back) and Privileged.

What the simulation got right, and what it left out

The attacks are rules, not a kernel: each rule states the documented effect of a Linux or Docker setting (capabilities, user namespaces, seccomp, mounts, cgroup limits). That keeps the project runnable anywhere and the output exact. The Pod Security Standards checks follow the Baseline and Restricted profiles of the Kubernetes documentation.

What it costs

  • Read-only file systems need writable scratch space (a tmpfs for /tmp, volumes for data), and applications that write next to their code must be changed.
  • Non-root needs the image prepared: file ownership, ports above 1024 (or the NET_BIND_SERVICE capability), and a user that exists.
  • Limits need numbers from load tests; too low gives out-of-memory kills, too high protects nothing.
  • The default seccomp profile is generous on purpose. A custom profile for your application is stronger and costs maintenance.
  • Hardening is not isolation. Containers share the host kernel: a kernel bug can still escape. For hostile code use a sandboxed runtime or virtual machines.

When this is too much

Do not turn every flag on at once without tests: add one setting, run the application's tests and a smoke test, and record the result. And do not mistake the container for the whole defence: network policy, secrets management and patching still apply.

Where you have already met this

  • docker run --privileged and -v /var/run/docker.sock:/var/run/docker.sock in tutorials.
  • securityContext in Kubernetes manifests, and Pod Security admission labels.
  • Distroless and non-root base images.
  • A scanner report titled "container runs as root".

Where this sits

This project is in platform-hardening and follows linux-hardening: the host settings below the container. The Docker and kind version (container-hardening-with-docker-and-kind) applies these flags to real containers and enforces Pod Security Standards.
