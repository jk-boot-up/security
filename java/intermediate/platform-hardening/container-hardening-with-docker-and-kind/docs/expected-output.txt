ONE. What docker run with no options gives an attacker.
  THE LAB:
    image    shop-app:probe, from alpine:3.24.3
    users    app (10001) owns /app; the image runs as root
    secret   DB_PASSWORD, in the environment
    probes   13 shell attempts, run inside the container
    seccomp  a profile file that denies 35 system calls,
             the ones Docker's own default profile denies
  THE OPTIONS (only the filter, as Docker would add it):
    docker run \
      --security-opt seccomp=<profile> \
      shop-app:probe
  WHAT THE PROBES READ:
    id -u        0 (root)
    CapEff       00000000a80425fb (14 capabilities)
    Seccomp      2 (a filter is on)
    memory.max   max (no limit)
    pids.max     max (no limit)
  HOW THE CAPABILITY MASK IS READ (CapEff 00000000a80425fb):
    bits set   0, 1, 3, 4, 5, 6, 7, 8, 10, 13, 18, 27, 29, 31
    names      CHOWN, DAC_OVERRIDE, FOWNER, FSETID, KILL, SETGID,
               SETUID, SETPCAP, NET_BIND_SERVICE, NET_RAW,
               SYS_CHROOT, MKNOD, AUDIT_WRITE, SETFCAP
    NET_RAW    (0xa80425fb >> 13) & 1 = 1, held
    SYS_ADMIN  (0xa80425fb >> 21) & 1 = 0, not held
  THE ATTEMPTS, BY WHAT THEY REACH:
    inside the container:
      read-secrets        POSSIBLE DB_PASSWORD is in the env
      tamper-with-app     POSSIBLE /app/shop.jar is writable
      drop-and-run        POSSIBLE a script in /tmp runs
      become-root         POSSIBLE id -u is 0
    the kernel:
      dangerous-syscalls  blocked  Seccomp is 2: a filter is on
      sniff-network       POSSIBLE the NET_RAW bit is set
      mount-host          blocked  mount tmpfs was refused
    the host:
      docker-socket       blocked  no Docker socket
      host-files          blocked  no host directory mounted
      host-network        blocked  its own network namespace
      see-host-processes  blocked  its own process namespace
    the node's resources:
      exhaust-memory      POSSIBLE memory.max is max
      fork-bomb           POSSIBLE pids.max is max
  HOW THE COUNT IS MADE:
    container 4 + kernel 1 + host 0 + resources 2 = 7 of 13
TWO. The configuration from the tutorial.

  THE ATTEMPTS, BY WHAT THEY REACH:

      read-secrets        POSSIBLE DB_PASSWORD is in the env
      tamper-with-app     POSSIBLE /app/shop.jar is writable
      drop-and-run        POSSIBLE a script in /tmp runs
      become-root         POSSIBLE id -u is 0

      sniff-network       POSSIBLE the NET_RAW bit is set
      mount-host          POSSIBLE mount tmpfs worked
    the host:
      docker-socket       POSSIBLE the socket is mounted
      host-files          POSSIBLE /hostetc/passwd is there
      host-network        POSSIBLE it sees docker0 or veth
      see-host-processes  POSSIBLE more than 15 processes
    the node's resources:
      exhaust-memory      POSSIBLE memory.max is max
      fork-bomb           POSSIBLE pids.max is max
  HOW THE COUNT IS MADE:
    container 4 + kernel 3 + host 4 + resources 2 = 13 of 13
THREE. One setting at a time.
  BEFORE THE STEPS:
    the tutorial configuration        13 of 13
  THE STEPS (one option more each time):
    1 no host access, not privileged   8 of 13
        blocks mount-host, docker-socket, host-files,
               host-network, see-host-processes
    2 a seccomp profile                7 of 13
        blocks dangerous-syscalls
    3 drop all capabilities            5 of 13
        blocks tamper-with-app, sniff-network
    4 a user that is not root          5 of 13
        blocks become-root
        opens  tamper-with-app
    5 no new privileges                5 of 13
        blocks nothing
    6 read-only root, noexec /tmp      3 of 13
        blocks tamper-with-app, drop-and-run
    7 memory and process limits        1 of 13
        blocks exhaust-memory, fork-bomb
  AFTER THE STEPS:
    1 of 13 possible: read-secrets
  WHY STEPS 3, 4 AND 5 LOOK ODD:
    3: root without DAC_OVERRIDE cannot write app's files
    4: user app owns /app, so it can change it again
    5: the image has no set-user-id program to stop
FOUR. The hardened container.
  THE OPTIONS:
    docker run \
      --security-opt seccomp=<profile> \
      --cap-drop ALL \
      --user 10001 \
      --security-opt no-new-privileges \
      --read-only \
      --tmpfs /tmp:rw,noexec,nosuid \
      --memory 512m \
      --pids-limit 200 \
      shop-app:probe
  WHAT THE PROBES READ:
    id -u        10001 (not root)
    CapEff       0000000000000000 (0 capabilities)
    Seccomp      2 (a filter is on)
    memory.max   536870912 (536870912 / 1048576 = 512 MiB)
    pids.max     200 processes
  THE ATTEMPTS, BY WHAT THEY REACH:
    inside the container:
      read-secrets        POSSIBLE DB_PASSWORD is in the env
      tamper-with-app     blocked  /app/shop.jar not writable
      drop-and-run        blocked  a script in /tmp cannot run
      become-root         blocked  id -u is not 0
    the kernel:
      dangerous-syscalls  blocked  Seccomp is 2: a filter is on
      sniff-network       blocked  the NET_RAW bit is clear
      mount-host          blocked  mount tmpfs was refused
    the host:
      docker-socket       blocked  no Docker socket
      host-files          blocked  no host directory mounted
      host-network        blocked  its own network namespace
      see-host-processes  blocked  its own process namespace
    the node's resources:
      exhaust-memory      blocked  memory.max is set
      fork-bomb           blocked  pids.max is set
  HOW THE COUNT IS MADE:
    container 1 + kernel 0 + host 0 + resources 0 = 1 of 13
FIVE. Settings that look harmless.
  BEFORE: the hardened container
    1 of 13 possible
  AFTER: hardened + --cap-add NET_RAW
    1 of 13 possible
    newly possible: nothing
    sniff-network       blocked  NET_RAW works only for root
  AFTER: hardened + --user 0 --cap-add SYS_ADMIN
    2 of 13 possible
    newly possible: become-root
    mount-host          blocked  the seccomp profile denies mount
  AFTER: the same, and seccomp=unconfined
    4 of 13 possible
    newly possible: become-root, dangerous-syscalls, mount-host
  WHAT IT SHOWS:
    each layer covers for a mistake in the others
SIX. The same on Kubernetes, with Pod Security Standards on kind.
  THE LAB:
    cluster     one kind node, itself a container
    namespaces  enforce privileged, baseline, restricted
    pods        the tutorial's, a plain one, the hardened one
    how         kubectl apply --dry-run=server: only the
                admission decides, nothing is created
  THE ADMISSION DECISIONS (refused: how many checks fail):
    pod         privileged    baseline      restricted
    tutorial's  admitted      refused (3)   refused (7)
    plain       admitted      admitted      refused (4)
    hardened    admitted      admitted      admitted
  WHY BASELINE REFUSES THE TUTORIAL'S POD:
    host namespaces
    hostPath volumes
    privileged
  WHY RESTRICTED REFUSES THE PLAIN POD:
    allowPrivilegeEscalation != false
    unrestricted capabilities
    runAsNonRoot != true
    seccompProfile
  A NAMESPACE THAT ONLY WARNS (enforce privileged):
    the plain pod is created: yes
    the warning lists 4 restricted checks
  THE RUNNING PODS, PROBED FROM INSIDE:
    plain, in baseline        7 of 13
      read-secrets, tamper-with-app, drop-and-run, become-root,
      dangerous-syscalls, sniff-network, exhaust-memory
    hardened, in restricted   2 of 13
      read-secrets, drop-and-run
  WHAT THE STANDARDS DO NOT COVER:
    they judge the pod's spec once, when it is created
    a writable emptyDir /tmp still runs a dropped script
    whoever can edit the namespace labels sets the standard
    the application can still read its own secrets
