THREE. The decisions a person makes, in the recipe.
  no second root account and no test account; a locked service account with no login shell; sshd_config with root login, passwords, empty passwords and X11 off;
  private modes for the key, the config and cron; no copied shell with the set-user-id bit; one listener, port 8080; the process runs as app, not root;
  and the namespaced kernel settings the container is started with: accept_redirects 0 and syncookies 1
  shop-host:hardened, scanned the same way: 0 findings
  the user the image's process runs as: root in the typical image, app in the hardened one
  the process of the hardened container runs as: app
FOUR. Running it again.
  someone loosens the config file inside a running container: [loose-permissions - /opt/app/config.properties, world-writable-file - /opt/app/config.properties]
  a new container from the image: 0 findings
  the scan is part of the build, on the image after it is built, and a regression fails it; on running containers it finds drift, and the answer to drift is a new container
FIVE. The bill.
  kernel.randomize_va_space inside the container is the host kernel's: 2; writing 0 to it from inside: refused (read-only file system)  <- A CONTAINER SHARES THE HOST'S KERNEL, SO THESE CHECKS ARE THE HOST'S TO FIX
  the scan runs as root inside the container, so it reads what a root process would; a process that runs as app sees less, and an attacker starts as that process
  the allow-lists, port 8080 and no set-user-id file, are the shop's own decisions; a scan with the wrong lists is either silent or noisy
  an image scan sees one moment of one container; what is added at start-up, or by a volume or an environment variable, is another scan
  how a container is started, with which user, capabilities, mounts and filesystem mode, is the subject of container-hardening
