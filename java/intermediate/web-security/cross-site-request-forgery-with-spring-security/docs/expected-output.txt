ONE. CSRF protection switched off, as many tutorials do to make a POST work.
  the web chain has http.csrf(c -> c.disable()); ana signs in: 302, 200 balance 1000
  a page on evil.example posts a transfer; the browser adds ana's session cookie: 200 sent 500 to mallory  <- A TRANSFER ANA NEVER ASKED FOR
  balances now: ana 500, mallory 500
TWO. Spring Security's default: a token tied to the session.
  the sign-in form itself needs a token, or anyone could sign a victim in to the attacker's account: without one 403, with one 302
  the token is renewed when ana signs in, so the one from before the sign-in no longer works: 403 Forbidden
  evil.example posts the same form without a token: 403 Forbidden
  with a real token from mallory's own session: 403 Forbidden
  ana's own form, with her token: 200 sent 20 to mallory
  the token is masked with a new random value on every page, so the same token never appears twice (a defence against BREACH): true
  and every masked token is accepted: 200
  logging out is a state change too: POST /logout without a token 403, with one 302
  balances now: ana 960, mallory 40
THREE. A single-page app: the token in a cookie that the page's script reads.
  the XSRF-TOKEN cookie is set, and HttpOnly is false: the script has to read it, so a script injected by cross-site scripting can too
  evil.example posts without the header: 403 Forbidden
  with the value from mallory's own cookie: 403 Forbidden
  the bank's own script copies the cookie into the X-XSRF-TOKEN header: 200 sent 20 to mallory
  evil.example cannot do that copy: a browser lets a page read only its own site's cookies
  balances now: ana 980, mallory 20
FOUR. What the default does not cover.
  the payment provider's webhook is exempt from tokens, because it has no session: a forged post with ana's cookie and no signature: 401 bad signature
  the exemption is safe only because the route checks its own proof: with the signature, 200 payment noted
  a route that moves money on GET, from a link on evil.example: 200 sent 100 to mallory  <- SPRING DOES NOT CHECK GET FOR A TOKEN
  the same transfer to a route that needs POST: 405  <- GET MUST NEVER CHANGE STATE
  balances now: ana 900, mallory 100
  a developer adds /transfer to the exemptions to make a test pass; evil.example posts: 200 sent 500 to mallory  <- ONE LINE OF CONFIGURATION UNDID THE DEFENCE
FIVE. The bill.
  the session cookie by default: HttpOnly true, SameSite false
  the API chain takes credentials in a header and keeps no session: ana's cookie from evil.example, no header: 401 Unauthorized
  the app that holds the credentials: 200 sent 20 to mallory
  so the API chain can leave CSRF off, because a browser never adds a header it was not given
  every state-changing route of the web chain, posted from evil.example with no token: 3 of 3 refused with 403
  with server.servlet.session.cookie.same-site=lax: SameSite=Lax is true; it is one more layer, and the token is still needed
