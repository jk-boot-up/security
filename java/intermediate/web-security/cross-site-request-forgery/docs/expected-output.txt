ONE. A request Ana did not intend.
  Ana logs in at the bank, and her browser keeps the session cookie: balance 1000
  in another tab she opens a page on evil.example, whose hidden form posts to the bank: send 500 to mallory
  the bank answers: 200 sent 500 to mallory  <- A TRANSFER ANA NEVER ASKED FOR
  balances now: ana 500, mallory 500
  the browser added Ana's cookie because the request went to the bank; the cookie proves who, not what she meant
TWO. A token in every form.
  the bank's own transfer form carries a token tied to Ana's session: true
  Ana sends 20 with the bank's form: 200 sent 20 to mallory
  the page on evil.example posts the same form without a token: 403 no form token
  with a real token from Mallory's own session: 403 the form token does not belong to this session
  evil.example cannot read Ana's token: the form lives on the bank's pages, and a browser does not let another site read them
  the token is compared in constant time, so the time an answer takes does not reveal how much of a guess was right
  balances now: ana 980, mallory 20
THREE. SameSite cookies.
  SameSite=Lax: the forged post from evil.example arrives without the cookie: 401 not logged in
  SameSite=Lax: a link on evil.example to the bank still opens Ana's account: 200 balance 1000
  SameSite=Lax: the bank's own form still works: 200 sent 20 to mallory
  SameSite=Strict: the same link from evil.example arrives without the cookie: 401 not logged in, so Ana looks logged out
  SameSite=Strict: typing the bank's address works: 200 balance 1000
  no SameSite at all: a modern browser treats the cookie as Lax: 401 not logged in
FOUR. Where the request came from, and GET.
  the browser says Sec-Fetch-Site: cross-site, and the bank refuses: 403 Sec-Fetch-Site is cross-site: a state-changing request must come from the bank's own pages
  the bank's own form says same-origin: 200 sent 20 to mallory
  an older browser sends no Sec-Fetch-Site, so the bank reads Origin: 403 Origin is https://evil.example, not the bank
  with neither header, only the token is left: these checks add depth, they do not replace it
  a bank that moves money on GET, with a Lax cookie: a link on evil.example: 200 sent 100 to mallory  <- GET MUST NEVER CHANGE STATE
  Lax lets cookies ride on top-level links, which is safe only because a link should never act
  the same link to a bank that needs POST: 405 a transfer needs POST
FIVE. The bill.
  SameSite as the only defence, in an older browser that ignores it: 200 sent 500 to mallory
  SameSite=Strict, and a page on reviews.bank.example, where customers post content: 200 sent 500 to mallory  <- SAME SITE, SO THE COOKIE IS SENT
  the same page, with tokens switched on: 403 no form token
  a bank page that forgot to include the token refuses Ana herself: 403 no form token, so the token must reach every form and client
  the bank's API takes a token in an Authorization header; evil.example's script cannot add a header it does not know: 401 no API token
  Ana's own app, which holds the token: 200 sent 20 to mallory
  so APIs with bearer tokens are not exposed the same way, as long as the token is not kept in a cookie
