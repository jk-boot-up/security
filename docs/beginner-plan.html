Plan: Beginner Track

Status: draft, 17 October 2026.

This plan covers the Beginner: Foundations section of the README. It is self-contained: sections 3 to 8 define the structure, tooling, audio, video, animation and YouTube standards for this repository.

1. Goal

Every beginner topic becomes one or more small, runnable teaching projects. Each project has:

  1. Java 25 (JDK 25) + Gradle code with deterministic tests.
  2. Two kinds of version where feasible: without tools (plain JDK) and with tools. A tool is anything that runs on the learner's own machine: a framework or library (Spring Security, Spring Boot, Bouncy Castle, Tink) or local infrastructure (Docker, Docker Compose, Kubernetes through kind, Terraform, nginx, Keycloak, CoreDNS, MinIO, LocalStack, OpenSSL, Wireshark, Trivy and similar). Python is also allowed, for helper scripts, small attacker or checker tools (for example packet crafting with Scapy) and the repository's own tooling. A topic gets only one version when the other would add nothing. Section 4 marks each case.
  3. An interactive animation in the browser, voiced step by step.
  4. A narrated video uploaded to YouTube.

Language plan: Java now (plain and with tools); Go and C++ later, in the same folder structure (section 3).

All labs run locally. No cloud account, no hosted lab service. Any open-source or free tool that runs on the learner's machine is allowed. Anything that needs a download (container images, a vulnerability database) is called out in the project's prerequisites.md, and the demo runs without the internet once those are in place.

2. Principles

  • Beginners first. Plain words, short sentences, one idea at a time. Every term is explained where it first appears.
  • Works with the eyes closed. Narration never says "as you can see". It names the actors and describes the flow in order.
  • Show it broken first. Each project runs the naive or insecure version, shows exactly how it fails, then the fix, then what the fix costs and where it is not enough.
  • Only two domains are used, in every security project: an online store (e-commerce) or a bank (banking). Each topic picks whichever of the two teaches it better: the store for orders, carts, customers, staff roles and traffic spikes; the bank for accounts, transfers, statements and money-sensitive trust. A project never uses a third domain. The chosen domain is named in the topic's concept.toml and README, and every language uses the same one. Analogies in the narration may come from anywhere (a vault, a hotel key card), but the code and the worked example stay in the store or the bank.
  • Deterministic. Fixed seeds, fixed clocks, no Thread.sleep, no real internet at run time. Every run prints the same numbers, and tests assert every number the demo prints. Tool versions and container images are pinned to exact versions.
  • Defensive and educational only. Attacks are shown against code and containers in the same project, on the learner's own machine (loopback or a local Docker network), so the learner sees why the defence exists.
  • Concepts first, patterns later. This track teaches the concepts underneath security patterns such as authorization policies, input validation, secrets management and token authentication. The patterns themselves belong to later tracks.

3. Repository layout

The language is the top-level folder, so Go and C++ can be added later as parallel trees with the same module and project names. Java is first.

Rules

  • Project names: <concept> for the plain version and <concept>-with-<tool> for each tool version. Names use no language word; the language comes from the top-level folder. The two sort next to each other, and a concept with several tools gets one project per tool.
  • Every project is self-contained, with its own build, tests, docs, diagrams, animation, video scripts and (where used) its own infra/ folder. Nothing is shared at run time, so a learner can copy one project out and run it.
  • Module folders hold a README (the projects in reading order, and how each builds on the last) and docs/spec.md plus docs/implementation-plan.md, which fix what the module's projects are before any of them is written. Each module also states one shared feature or scenario and a forced change that its projects are judged by, where that applies.
  • Plain is always the standard library only. A tool project depends on the tool and says so in its prerequisites.md.
  • Build files by language: Java uses a Gradle wrapper with a JDK 25 toolchain (the build picks the right JDK itself; each prerequisites.md names the exact JDK and Gradle versions). Go uses go.mod. C++ uses CMakeLists.txt, with vcpkg.json or conanfile.txt for projects that need libraries.
  • Local infrastructure (Docker Compose files, nginx or CoreDNS configuration, kind manifests, Terraform, Python helpers) lives in the project's infra/ folder, with container images pinned to exact versions.
  • Tests stay fast and deterministic. The default test task (./gradlew test) never needs Docker. Tests that need containers run through a separate integrationTest task that starts and stops the containers itself.
  • Package and module roots: Java com.jk.explore.security.<concept>; Go github.com/jk-boot-up/security/go/beginner/<module>/<project>; C++ namespace jk::security::<concept>.
  • Across languages, the teaching is identical. A concept uses the same module, project name, domain, scenario, acts and numbers in every language. Each project keeps its golden demo output in docs/expected-output.txt; a port copies that file and its tests compare against it. The first Java project fixes the golden output, and ports follow module by module once the Java module is finished and stable.
  • Videos are per project, because the code on screen differs. Each project has its own video/ and youtube.md, and playlists name the language (section 8).

5. Tooling

This repository carries its own small toolset under tools/, built in Phase 0:

Tool Job
scaffold create a module folder or a project: build files, package layout, voice settings, starter concept.toml
docgen generate the Markdown and HTML docs, diagrams, animation page and video scenes from concept.toml
videokit narration (Piper), slides, video, captions and animation audio, as one library; a project's video/ folder holds only its content
ytupload prepare the upload sheet; later, the scripted YouTube Studio upload and the link registry

One command builds a project end to end: tests, docs, diagrams, animation, video and index.

The tools must support the language / track / module / project layout of section 3, with per-language build and test commands (Gradle, go test, CMake with CTest) and per-language thumbnails and playlists. They are written once and shared by every language.

6. Audio and video

Every video and animation follows the video and animation teaching standard: pictures with real examples, input and result in separate sections, derived values worked out step by step, every acronym spelled out, and a short tour of the Java classes.

  • Voice: Piper en_US-amy-medium, speed 0.8, sentence_gap = 0.7, pause_scale = 1.5, −16 LUFS, peaks limited to −1.5 dBFS. Written to each project's video/videokit.toml.
  • Credit is always third person: "This video is presented by Jayasekhar Konduru." No first-person narration.
  • "ID" is spoken "I D". Numbers and symbols are spoken as words.
  • Opening order:
  • what the video is: "This video explains X, in Java.";
  • the credit;
  • a plain definition;
  • the same idea taught in the topic's domain, the online store or the bank.
  • Closing: one-sentence lesson, the repository, a like and a subscribe, thanks. Never name the next video.
  • Length: as short as the teaching standard allows; about 30 to 36 scenes with the pictures and the class tour.
  • Quality gates: continuous audio, no first-person credit, captions timed from the recorded phrases. A build fails rather than ship a bad video.
  • Picture: slides are laid out in 1920×1080 units but drawn and encoded at 3840×2160 (H.264, CRF 18, BT.709 colour written into the file). YouTube gives 4K uploads its high-bitrate encodes, so slide text stays sharp even when watched at 1080p.
  • Readable text: body text 40 to 52 px and console text 34 to 48 px (in 1920×1080 units); long console lines wrap rather than shrink, long titles take two lines, and secondary lines are light grey, never dim.
  • Title frame: the project's cover, the same design as its thumbnail (cyan theme, the author's photo, the topic's key cards) with "Presented by Jayasekhar Konduru" and the line "GitHub: https://github.com/jk-boot-up/security/". Drawn by tools/videokit/videokit/slides/cover.py from cover_cards.py.
  • End frame: the same cyan theme, the author's photo, Like / Subscribe / Share, "GitHub Repo: github.com/jk-boot-up/security/" (taken from docs/youtube.md, without https://) and "Authored by Jayasekhar Konduru".
  • Security-specific wording: an attack is always described as "the attacker" acting on the project's own demo code. No instructions aimed at real systems.

7. Animation

  • docs/animation.html per project, one step per act, generated from concept.toml.
  • Narration in the amy-slow voice only, rendered by videokit.sh animation <project> into docs/audio/ and injected between the videokit:narration markers. Audio is never embedded in the HTML.
  • The shared UX layer: Light / Dim / Dark theme, clickable timeline, Back button, progress bar, Predict first, keyboard control, an All-steps list, no sideways scrolling at phone width, reduced motion respected.
  • A Narration on/off toggle and a Play / Pause / Resume button for the step on screen.
  • Without the audio clips, the page still works silently.

8. YouTube

Files uploaded: the .mp4 (which already contains the narration), the matching .srt, and the project's docs/thumbnail-security-photo-cyan-theme.png (1280×720). The .m4a is never uploaded.

Text rules:

  • No http:// or https:// in the description; the repository link reads github.com/jk-boot-up/security/tree/main/<language>/beginner/<module>/<project>.
  • No < or > in the title or description.
  • The first sentence is the name and plain definition: "X in Java: ...".
  • Chapters are timed from the uploaded video's own .srt: start at 00:00, at least three.
  • Title at most 100 characters (aim for 60), description at most 5,000, tags at most 500.
  • Every video's tags include the author's name, "Jayasekhar Konduru", and the repository, "github.com/jk-boot-up/security/", so a search for either finds all of them. The playlist named in each sheet is the project's own module playlist.

Settings: uploaded Unlisted, made Public once the quality check passes; not made for kids; no paid promotion; altered content No; category Science & Technology; language English set before subtitles; captions from the .srt; thumbnail uploaded; end screen to an already published video; never announce a next video.

Playlists: per language, then two per module, never mixed. The tables below are the Java playlists. Go and C++ get the same set with "in Go" or "in C++" in place of "in Java", created on the first upload for that language.

Videos sit in learning order. Playlist names are placeholders until the first upload.

No uploads before review. Nothing is uploaded, scheduled or published until the author has reviewed that project's rendered video, animation and docs and asked for it. Until then the pipeline stops at the local build: the upload step is limited to printing the upload sheet (ytupload.sh sheet), which sends nothing. Approval is per project, or per batch if the author says so.

Process: the scripted uploader drives YouTube Studio in a Chrome window the channel owner has signed in to by hand. It never types a password and runs only when the owner asks. Uploads happen one video at a time, a failure never causes a duplicate, and every link is recorded in docs/youtube-links.json, which feeds the index.

Quality check: every upload goes through tools/ytupload/ytquality.sh run <targets>, one video at a time, in learning order. For each video:

  1. Local check of the .mp4 before anything is sent: 3840×2160; every slide's text matches the slide (brightness SSIM ≥ 0.985 at 1080p, sharpness ≥ 93 % of the slide's); loudness −18 to −14 LUFS; peaks below 0 dBTP; no silence longer than 4 s.
  2. Upload Unlisted, with every field filled and the custom thumbnail (no thumbnail, no upload).
  3. Check YouTube's copy: wait until YouTube serves 1080p and 4K, download the 1080p stream browsers play and its audio, and check them: slide text (SSIM ≥ 0.95, sharpness ≥ 80 %), loudness, peaks, silences, length within 1 s of the video, a 4K version exists, and the thumbnail shown is the custom one.
  4. Pass: the video is made Public. Fail: the copy is deleted from YouTube, the video is rebuilt with stronger settings (try 2: CRF 14, 256 kbit/s audio; try 3: CRF 10, 320 kbit/s) and steps 1 to 3 run again.

At most three tries per video. After the third failure the copy is deleted, the video is marked failed, and the run stops: the next video is not started until the current one passes. Every try (settings, measurements, problems, video ID) is recorded in docs/youtube-quality.json and summarised in youtube.md. The script only ever deletes a copy it uploaded itself.

A Studio or network hiccup is not a failed try: the video is retried after 10 minutes (an unchecked copy left behind is deleted first), and the run stops after three hiccups on the same video. For a long unattended run, keep the Mac awake (caffeinate -i -s): idle sleep pauses the run and makes Studio time out. A video built ahead of time with the try 1 settings (CRF 18, 192 kbit/s) and marked in video/build/quality-settings.json is not built again, so videos can be built in the background while others upload. Pause those builds while the script talks to Studio. Keep 1-pixel decoration (grids, hairlines) off full-frame slides: YouTube's encoding erases it, so its copy no longer matches the slide even when the text is perfectly readable.

Never committed: .mp4, .m4a, .srt, .wav, audio clips, build output.

9. Phases

Phase 0: Set up (once)

  1. Build the tools in section 5, starting with scaffold and videokit.
  2. Create java/beginner/ with its README and module folders.
  3. Add a .gitignore for rendered media and Gradle output.
  4. Add a repo-level generator for the index and the YouTube registry.
  5. Build project 1 end to end as the pilot: code, docs, diagrams, animation, video, thumbnail, a dry-run upload sheet (no upload). Fix the pipeline before building the rest.

Phase 1: Build the modules, one project at a time

For each project:

  1. Scaffold it.
  2. Write the insecure version, the secure version and the demo, in 4–6 acts with exact numbers.
  3. Write the tests; run ./gradlew test run until green and the output reads well.
  4. Write concept.toml using the numbers the demo actually printed.
  5. Generate docs, diagrams and animation; check the README, one diagram and the animation page.
  6. Render the video and animation audio in the background and move on.
  7. Tick the checklist.

Order: modules 1 to 7, plain version first, then the with-tools version of the same topic. This phase is Java only.

Phase 1b: More languages (later)

Per module, once its Java projects are done and their expected-output.txt files are stable:

  1. Add the module's projects under go/beginner/<module>/, with the same project names, then the -with-<library> projects.
  2. Copy each project's docs/expected-output.txt, run the demo and diff its output against it.
  3. Adapt concept.toml for the code on screen and render the video. Upload only after review, as in Phase 2.
  4. Repeat for cpp/.

Library candidates, to be confirmed when the time comes: Go golang.org/x/crypto, crypto/tls, net/http; C++ OpenSSL, libsodium, Botan. Some projects may be skipped in a language where they add nothing (for example Spring Security has no Go twin; the Go project would use x/crypto and net/http middleware instead).

Phase 2: Publish

  1. Review each rendered video: first and last minute, credit line, no next-topic teaser.
  2. Upload only after the author has reviewed and approved a project's video, animation and docs, and only when the author asks for uploads. Then go module by module, one video at a time, plain playlists first.
  3. After each batch, regenerate the index and the registry.
  4. Commit and push source only. Media stays local.

10. Acceptance for each project

  1. ./gradlew test passes and ./gradlew run prints the acts.
  2. All files in section 3 exist. HTML pages inline styles and link images; no base64 images; no Mermaid.
  3. Video and animation are rendered in the amy-slow voice with no failed gate, and meet the teaching standard.
  4. The project appears in the beginner README and the index.
  5. Nothing rendered is committed.
  6. The demo attacks only its own code and containers, on the learner's machine.

12. Risks

  • Pinned versions age. Container images, tools and libraries are pinned for repeatable labs, and some pins are already the last of their kind (LocalStack 4.14.0 is the last community tag that starts without a token; the kind node is newer than the local kubectl). Once a year, refresh every pin to the latest stable release, rerun test and integrationTest, and record any pin that must stay.
  • Tooling is new work. The pilot project in Phase 0 proves the whole chain before the other projects are built.
  • Plain JDK has no public certificate-creation API. Test keystores are made with keytool by a Gradle task, so the plain version stays dependency-free; the with-tools version uses Bouncy Castle or OpenSSL.
  • Some demos need network features (DNS, TLS). All run on the learner's machine, against test servers or containers in the same project, never the real internet.
  • Tool variants need Docker (and kind for Kubernetes). They add setup, disk and memory cost, and Docker behaves slightly differently across macOS, Linux and Windows. Mitigations: a plain version always exists so the topic can be learned without Docker, images are pinned, container tests are kept out of the default test task, and prerequisites.md lists the exact versions and resources needed.
  • Dependency-hygiene tools download vulnerability data. This needs the internet but no account; the prerequisites page says so, and the demo can run against a bundled data snapshot.
  • Security content ages. Each project names the algorithm and library versions it uses, and the README says which choices are current as of the build date.
  • Misuse. Attacks are demonstrated only on the project's own code, and the README's ethics note applies to every project.
